# 架构

这份文档讲清两件事：系统由哪些部分组成，以及一条请求在其中怎么流动。

## 一、总体分层

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 接入层  CLI（kubedocs.cli）· HTTP API（api/）                              │
├──────────────────────────────────────────────────────────────────────────┤
│ 应用层  agent/（工具循环 · 图编排）· clinical/（医疗产品能力）             │
├──────────────────────────────────────────────────────────────────────────┤
│ 领域层  domains/（k8s_docs · clinic）——每个域自带语料、模型、检索与工具     │
├──────────────────────────────────────────────────────────────────────────┤
│ 能力层  retrieve/（混合检索 · 融合 · 重排）· generate.py（带引用回答）      │
├──────────────────────────────────────────────────────────────────────────┤
│ 数据层  ingest.py（摄取）· store/（sqlite · sqlite-vec · pgvector）       │
├──────────────────────────────────────────────────────────────────────────┤
│ 支撑    config.py · observability.py · evaluation/                        │
└──────────────────────────────────────────────────────────────────────────┘
```

依赖方向自下而上，上层不直接被下层 import 细节：域包通过 `DomainRegistry` 注册，
存储与重排都走接口，因此**换后端不改上层**。

## 二、域（Domain）

一个域是"一套语料 + 一套检索配置 + 一组工具"的组合。目前两个：

| 域 | 语料 | 嵌入模型 | 维度 | 用途 |
|---|---|---|---|---|
| `k8s_docs` | Kubernetes 官方文档 1720 篇 | `bge-small-en-v1.5` | 384 | 技术文档问答 |
| `clinic` | 医疗知识卡片 31,592 张 | `bge-small-zh-v1.5` | 512 | 问诊、分诊、挂号 |

域之间**完全隔离**：各自的索引目录（`<index-dir>/<domain>/`）与存储 schema，
向量维度与归一化器都不同。共用一份索引只会把两套数据混进同一个矩阵，因此从设计上避免。

加一个域 = 新增一个域包（声明语料路径、嵌入模型、检索器、工具），在 `domains.load_all()` 注册一行。

## 三、检索链路

```
查询 ──► 归一化（可选中文分词）──┬──► 全文检索（BM25 / 数据库全文索引）
                                └──► 稠密检索（向量近邻）
                                          │
                                     RRF 融合（k=60）
                                          │
                                  可选重排（cross-encoder）
                                          │
                                       返回片
```

要点：

- **两路召回互补**：BM25 擅长精确术语与标识符（`terminationGracePeriodSeconds`），
  向量擅长同义与自然语言改写（"让每个副本有自己的名字和磁盘"）。
- **RRF 融合不依赖分数可比性**：只按名次融合，避免"向量相似度与 BM25 分数不同量纲"的问题。
- **重排默认关闭**：cross-encoder 质量更好但要多加载一个模型；按需开启。
- **降级是显式的**：任一路失败会退化为单路并在结果里记录原因，而不是静默返回空。

## 四、摄取链路

```
语料文件 ──► 切块 ──► 分批编码 ──► 写入（文档 / 块 / 全文索引 / 向量索引）──► 一致性自检
```

- **分批提交**：批大小决定"中断时最多丢多少工作"，默认小批量（60 个文件）。
- **增量与删除同步**：按文件内容指纹判断是否需要重新编码；限定文件范围的试跑会关闭删除同步，
  避免把范围外的内容当成"已删除"。
- **一致性自检**：向量行与块行必须一一对应，行数或连续性不一致就报错——这种错位一旦静默存在，
  检索结果会整体漂移。

## 五、Agent 与工具

工具的**唯一真相源**是 `agent/tools.py` 的 `ToolRegistry`。一个 `ToolSpec` 声明：
名称、说明、参数模型、"什么时候**不该**用"、是否产生副作用、执行体。

同一个注册表同时供给两个消费方，因此不存在"两份定义不一致"的问题：

- HTTP `GET /tools`（自省）
- Agent 工具循环（模型按需调用）

两条编排路径：

| 路径 | 机制 | 适用 |
|---|---|---|
| 图编排 | LangGraph `StateGraph`：红线检查 → 采集 → 工具循环 → 确认 → 应答，带真 `interrupt` 与可选 checkpointer | 需要严格流程与断点续跑的场景 |
| 工具循环 | 模型自行决定调用哪些工具，代码只提供清单、执行器、轮次上限与白名单 | 开放式问诊 |

共同约定：

- **有副作用的工具默认不暴露**，需要时显式开启；产生副作用前必须显式确认。
- **调用方身份不从模型来**：患者标识由调用方注入执行体，不在工具参数里，模型无法伪造。
- **轮次与证据都有上界**：工具循环轮次有硬上限，累积的证据条数也有上限。

## 六、医疗产品层（`clinical/`）

```
contracts.py    输出契约：ClinicalAssessment / RedFlag（病症 + 严重程度 + 依据）
triage.py       检索式分诊：粗排 → 精排 → 科室投票，叠加科室补全表
evidence.py     证据装配与渲染
intake.py       多轮采问：槽位采集与"最多问几次"的收敛
prompts/        系统提示词（硬性条款 R1–R7 与输出契约）
reasoning.py    主判：装配提示词、解析契约、失败降级、预算闸
orchestration.py 工具编排：模型自行决定取证
pipeline.py     把上面这些装成一条链
```

**一次问诊的形状**

```
患者发言
  │
  ├─ 采问：补齐关键信息；信息不足则追问（有次数上限，不会无限问）
  │
  ├─ 取证：模型调用工具（检索知识卡片、核对引用…）
  │        返回的证据由程序编号 K1、K2…，模型引用编号
  │
  ├─ 主判：输出结构化结论
  │        urgency · red_flags · departments · differentials
  │        exams · medications · patient_summary · followup_questions
  │
  ├─ 契约校验与执行
  │        · 判出急重症却给常规档 → 违规
  │        · 检查/用药没有依据 → 丢弃该条
  │
  └─ 应答：`patient_summary`（对话体）+ 急诊提示（如需）
```

**安全设计**

- **急诊判断由模型基于"病症 + 严重程度"给出**，并输出可审计的依据（`red_flags` 的每一条都要写清
  是什么病症、严重到什么程度、凭什么这么判）。
- **契约层守住唯一硬约束**：判出急重症却给常规建议属于自相矛盾，会被判违规。
- **依据约束**：检查与用药建议必须引用真实存在的证据编号；没有依据的条目会被丢弃。
- **急重症信息不被这条约束削弱**：急重症判断、科室建议与对话正文不因依据缺失而被删掉。

## 七、可观测与运维

- `GET /metrics`：Prometheus 指标，含按端点的请求数与耗时、检索各路耗时、LLM 花费与预算。
- `GET /healthz`：存活 + 当前域的块数与索引可用性。**索引不可用不算存活失败**，
  此时接口仍返回 200 并在 `diagnostics` 里说明原因，避免"探针把服务打成不健康"。
- 花费：所有模型调用共用一本日预算账本，账本按日累计落在 `data/index/llm_spend.json`。

## 八、关键目录

```
src/kubedocs/
  config.py        配置与路径锚定（含容器内覆盖）
  cli.py           命令行入口：ingest / search / ask / eval / serve / stats / domains …
  ingest.py        摄取流水线
  embed.py         嵌入器抽象（bge / hashing）
  normalize.py     归一化器（可选中文分词）
  generate.py      带引用回答与日预算账本
  store/           sqlite · sqlite-vec · pgvector
  retrieve/        混合检索、RRF、重排
  domains/         k8s_docs · clinic
  agent/           工具注册表、ReAct 循环、图编排
  clinical/        医疗产品层
  api/             FastAPI 端点数与页面
  evaluation/      评测闸门与基线
```

## 九、扩展点速查

| 想做的事 | 改哪里 |
|---|---|
| 加一个域 | 新增域包 + `domains.load_all()` 注册一行 |
| 加一个工具 | `agent/tools.py` 注册 `ToolSpec` |
| 加一步服务端编排 | `clinical/orchestration.py` 的工具循环 |
| 换嵌入模型 | 域包里的 `embedding_model`，然后**重建索引** |
| 换向量后端 | 配置 `KUBEDOCS_STORE`，实现新后端则加一个 `Store` 子类 |
| 换精排 | 实现重排接口（`retrieve/rerank.py`），在域包里启用 |
| 调分诊行为 | `clinical/triage.py` 的候选池大小与投票权重 |
| 改提示词 | `clinical/prompts/system.md`（内容变更会反映到提示词版本指纹） |
