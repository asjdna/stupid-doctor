# 架构

这份文档讲清两件事：系统由哪些部分组成，以及一条请求在其中怎么流动。

## 一、总体分层

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 接入层  CLI（kubedocs.cli）· HTTP API（api/）· MCP server（mcp/）        │
├──────────────────────────────────────────────────────────────────────────┤
│ 应用层  agent/（工具循环 · 确定性图＝对照臂）· clinical/（医疗产品能力）       │
├──────────────────────────────────────────────────────────────────────────┤
│ 领域层  domains/（k8s_docs · clinic）——每个域自带语料、模型、检索与工具     │
├──────────────────────────────────────────────────────────────────────────┤
│ 能力层  retrieve/（混合检索 · 融合 · 重排）· generate.py（带引用回答）      │
├──────────────────────────────────────────────────────────────────────────┤
│ 数据层  ingest.py（摄取）· parse.py（多格式解析）· store/（pgvector 等） │
├──────────────────────────────────────────────────────────────────────────┤
│ 支撑    config.py · observability.py · evaluation/                        │
└──────────────────────────────────────────────────────────────────────────┘
```

依赖方向自下而上，上层不直接被下层 import 细节：域包通过 `DomainRegistry` 注册，
存储与重排都走接口，因此**换后端不改上层**。

## 二、域（Domain）

一个域是"一套语料 + 一套检索配置 + 一组工具"的组合。目前两个：

| 域 | 语料 | 嵌入模型 | 维度 | 用途 |
|---|---|---|---|---|
| `k8s_docs` | Kubernetes 官方文档 1722 篇（随上游 main 分支漂移） | `bge-small-en-v1.5` | 384 | 技术文档问答 |
| `clinic` | 医疗知识卡片 31,592 张 | `bge-small-zh-v1.5` | 512 | 问诊、分诊、挂号 |

域之间**完全隔离**：各自的索引目录（`<index-dir>/<domain>/`）与存储 schema，
向量维度与归一化器都不同。共用一份索引只会把两套数据混进同一个矩阵，因此从设计上避免。

加一个域 = 新增一个域包（声明语料路径、嵌入模型、检索器、工具），在 `domains.load_all()` 注册一行。

### 语料按需装配：仓库里**不带语料**

上面两类语料都**不随仓库分发**（本仓库没有它们的再分发权，边界见仓库根的 `NOTICE.md`），
索引也不入库——所以一份新克隆出来的仓库**没有可检索的依据**。这不是缺陷：语料与索引都是
**派生物**，塞进仓库只会让它变成一份无法追溯许可的数据包。

没有语料时的行为是可预期的，也是设计的一部分：检索为空 ⇒ 约束层按
`no_medical_advice_without_evidence` **不给医学内容**（把那段散文换成只含事实的回答）。
判断力没有下降，是**依据没了**——系统不允许用模型的通用知识顶替检索结果。

接回来的三种方式：

| 方式 | 命令 | 说明 |
|---|---|---|
| k8s 官方文档 | `python scripts/fetch_corpus.py` | 从上游拉 `content/en/docs/**/*.md`（许可见 `NOTICE.md`） |
| clinic 知识卡片 | `python scripts/clinic_build_cards.py --source <上游产物目录>` | 需要上游 `build_knowledge.py` 的产物；脚本不猜机器上的路径 |
| **自己的文档** | `python -m kubedocs.cli --corpus-dir <你的目录> ingest` | 任意 `.md/.txt/.csv/.html/.pdf/.docx/.xlsx/.pptx`，域不关心来源 |

`clinic` 域吃的是**卡片表**而不是自由文档：`data/clinic/cards.json` 是一个数组，每张卡至少
`{"kind","key","text"}`，`diseases` / `departments` 供分诊投票。路径由 `clinic_cards_path()`
写死（**没有**环境变量可覆盖），所以要么换文件、要么加一个域。

⚠ **语料太小比没有语料更危险**（实测）：安全门判的是"**有没有依据**"，不是"依据相不相关"。
用一份只有 3 张卡片的索引去问它完全没涵盖的问题（实测：「脚踝扭伤两周、石膏什么时候能拆」），
检索仍会命中那 3 张卡，模型于是"有依据"地用自己的通用知识答了骨科问题——`safety` 不触发、
`contract_violations` 为 0。所以自带语料必须**覆盖你真正会问的范围**，读回答时也要核对
`reference.evidence_ids` 指向的卡片是否切题。

## 三、检索链路

```
查询 ──► 归一化（可选中文分词）──┬──► 全文检索（BM25 / 数据库全文索引）
                                └──► 稠密检索（向量近邻）
                                          │
                                     RRF 融合（k=60）
                                          │
                                  可选重排（cross-encoder）
                                          │
                                       返回片
```

要点：

- **两路召回互补**：BM25 擅长精确术语与标识符（`terminationGracePeriodSeconds`），
  向量擅长同义与自然语言改写（"让每个副本有自己的名字和磁盘"）。
- **RRF 融合不依赖分数可比性**：只按名次融合，避免"向量相似度与 BM25 分数不同量纲"的问题。
- **重排默认关闭**：cross-encoder 质量更好但要多加载一个模型；按需开启。
- **降级是显式的**：任一路失败会退化为单路并在结果里记录原因，而不是静默返回空。

### 检索用子块，生成用父块

索引里存着**两层**，由 `chunker.py` 一次切出：

| 层 | 是什么 | 进不进索引 | 它在回答什么 |
|---|---|---|---|
| 子块 `Chunk` | 标题小节内部的段落装箱（目标 300 字符、相邻重叠 60 字符） | 进：BM25 与向量都建在它上面 | "命中的是**哪一句**" |
| 父块 `Parent` | 一个标题小节；超过 3000 字符就按段落边界拆成几片 | 不进：不参与全文、也不算向量 | "这句话**前后在讲什么**" |

- **id 形状**：子块是 `<doc_id>::<四位序号>`，父块是 `<doc_id>::p<四位序号>`。
- **短碎片只在同一个父块内合并**。跨父块合并会把上一节的残句接到下一节的引用下，
  而引用说的还是上一节——这是必须避免的。
- **读路径统一走 `ChunkHit.context_text`**：有父块给父块，没有（索引里没有父块、或调用方不传
  父块）退回子块正文。取值一律用它，不要直接读 `parent_text`——那会把"没有父块"变成"喂给模型的
  上下文是空的"。

**为什么多存一层**：子块小 ⇒ 命中精确（一个具体说法、一行报错含义，而不是整节"泛泛相关"）；
父块完整 ⇒ 模型看得到前后文，不会拿着一句被切一半的话去答题。两层用途不同，谁都不能省。

**`body` 与父块是两种东西**，给模型时要一起给：`body` 是命中的那一段（短、已截断），
父块是它所在的整节（读得到语境）。只给前者，模型容易拿着断章下结论；只给后者并在长度上截断，
又可能把命中的那句整段截掉——命中在小节里的位置是不确定的。落点：
`generate.build_context` 用父块（按父块去重，`per_chunk_chars` 默认 3000）、
`agent/rag_tools.py` 的 `search_docs` 返回 `body` + `context`、
`clinical/evidence.py` 的 `EvidenceItem.text` + `.context`。

卡片语料（`clinic`）是唯一的例外：每张卡片本身就是一个原子知识单元，父块与子块**同文**
（理由见 [`DECISIONS.md`](DECISIONS.md)），父块行照写，读路径因此与文档语料完全一致。

**`top_k` 是按文档去重之后的条数**（`HybridRetriever._diversify`，同一篇文档最多
`KUBEDOCS_MAX_CHUNKS_PER_DOC` 条，默认 2）。这一步不能省：检索单位变小之后，同一节的
兄弟块会一起涌进前几名，实测 `top_k=10` 里平均只有 5.38 篇不同文档、最少的一次只有 2 篇
——用户看到的"前 10 条结果"里一半是同一篇文档的两段话。去重同时修好了 hit@k（0.78 → 0.86）
与真实体验；数字与口径见 [`EVALUATION.md`](EVALUATION.md)。

## 四、摄取链路

```
语料文件 ──► 解析（多格式 → 带位置的块）──► 切块（父子两层）──► 分批编码
        ──► 写入（文档 / 父块 / 子块 / 全文索引 / 向量索引）──► 一致性自检
```

- **分批提交**：批大小决定"中断时最多丢多少工作"，默认小批量（60 个文件）。
- **增量与删除同步**：按文件内容指纹判断是否需要重新编码；限定文件范围的试跑会关闭删除同步，
  避免把范围外的内容当成"已删除"。
- **一致性自检**：向量行与块行必须一一对应，行数或连续性不一致就报错——这种错位一旦静默存在，
  检索结果会整体漂移。

### 多格式解析：位置是引用可信的前提

`parse.py` 把任意受支持的资料转成**带位置的块**，切块仍然全部由 `chunker.py` 负责。
受支持的后缀：`.md` / `.txt` / `.csv` / `.html` / `.htm` / `.pdf` / `.docx` / `.xlsx` / `.pptx`。

**位置语义按格式分别定义**，不做"统一成行号"这种会把语义抹平的归一：

| 格式 | 位置 | 切块粒度 |
|---|---|---|
| `.pdf` | `p.7`（页码，1 起） | 按页 → 页内再按段 |
| `.xlsx` / `.csv` | `Sheet1!A1:C20`（sheet 名 + 行区间） | 按行窗口，**每块重复表头行** |
| `.pptx` | `slide 3` | 按幻灯片（标题 + 要点 + 备注） |
| `.docx` / `.html` / `.md` / `.txt` | 标题路径（h1–h6） | 按标题切小节 |

位置以**面包屑首段**的形式进入引用（`[手册.pdf › p.7]`、`[台账.xlsx › Sheet1!A1:C20]`），
所以不新增存储字段；容器型格式的父块**不跨位置**——跨页/跨表合并会把下一页的文字挂到上一页的
引用下。

三条不变量（都会毁掉现场演示，所以写在 `parse.py` 顶部）：

- **绝不静默丢字**：编码按 `utf-8-sig` → `utf-8` → `gb18030` 严格探测，全失败才取"替换字符更少"
  的那个用 `errors="replace"` 救回来，并把替换字符数写进报告。**不用 `errors="ignore"`**——
  丢字是静默的，而"少了几行"在检索里表现为莫名其妙的漏召回。
- **扫描件点名跳过**：PDF 抽出空文本 = 无文本层（不做 OCR），报"该文件无文本层（疑似扫描件），
  已跳过"并计数，**绝不建空块**。"库里有这个文档但搜不到"必须能查出原因。
- **单文件失败不影响整批**：`parse()` **不抛异常**，任何失败（不支持的格式、文件损坏、缺解析库）
  都变成可读原因，计进摄取报告，本批继续。

解析库（`pypdf` / `python-docx` / `openpyxl` / `python-pptx` / `beautifulsoup4`）都在
`pyproject.toml` 里显式声明，且都是**函数内延迟 import**：缺一个库只坏一种格式，不会让
`import kubedocs.ingest` 整体失败、连检索服务都起不来。

## 五、存储后端（pgvector / sqlite-vec / sqlite）

`store/` 下是同一份 `Store` 协议的三套实现，按 `KUBEDOCS_STORE` 选：

| 取值 | 实现 | 定位 |
|---|---|---|
| `pgvector`（默认） | `PgVectorStore` | Postgres + pgvector HNSW：近似检索、**一库同时承担全文与向量**、索引跨重启与多副本共享 |
| `sqlite-vec` | `SqliteVecStore` | 离线回退：零外部进程、零镜像、零网络 |
| `sqlite` | `SqliteStore` | numpy 暴力内积 + `.npy` 侧车矩阵：最小依赖，兼作性能对照 |

三个实现都是**同一套父子两层的读法**：父块存在普通表里、由子块的 `parent_id` 指过去，
命中后批量取回。**没有父块数据的索引可以原地升级**（例如更早的版本写下的那一份）：
打开时幂等地补上父块表与 `parent_id` 列，已有子块行不动；缺父块的行 `parent_text` 为空串，
`context_text` 于是退回子块正文。

**两条失败路径刻意不同**（`store/__init__.py` 的 `from_settings`）：

- **非法取值直接报错**，绝不静默回退——回退成默认后端会让"我明明切到 pgvector 了，
  为什么数据还是旧的"变成一个没有任何日志的谜。
- **数据库不可达则降级为 `sqlite-vec`**，把原因写到返回对象的 `fallback_reason` 上；
  传 `allow_local_fallback=False` 可以让它原样抛错，留给"基础设施没起就该响亮失败"的调用方。

**降级是可见的，也是有代价的**。可见的落点：

- `GET /healthz` 的 `store`（实际生效的后端类名）与 `store_fallback`（降级原因）；
- CLI `stats` 打印「存储后端 X（配置 Y）」，降级时再打一行 `⚠ 已降级：…`，
  JSON 里多出 `store_backend` / `store_configured` / `store_fallback` / `n_parents`。

代价是**两个后端的索引存在不同位置**：降级期间建的索引在 Postgres 恢复后是**看不见**的。
要回到生产后端，先起数据库再重跑 `ingest`。

## 六、Agent 与工具

工具的**唯一真相源**是 `agent/tools.py` 的 `ToolRegistry`。一个 `ToolSpec` 声明：
名称、说明、参数模型、"什么时候**不该**用"、是否产生副作用、执行体。

同一个注册表同时供给两个消费方，因此不存在"两份定义不一致"的问题：

- HTTP `GET /tools`（自省）
- Agent 工具循环（模型按需调用）

**请求路径只有一条：工具循环。** 模型通过 function calling 自己决定调哪些工具、调几次，
代码只提供清单、执行器、轮次上限与白名单。

另有一条**确定性图**（LangGraph `StateGraph`：红线检查 → 采集 → 工具循环 → 确认 → 应答，
带真 `interrupt` 与可选 checkpointer，见 `agent/kernel.py` 的 `ClinicAgent`）。
它**不在任何请求路径上**——`/chat` 只走工具循环。保留它有两个用途：评测里拿它跑同一批
问题，比较"规则判断 vs 模型判断"的差异；单元测试直接调它做回归。
**新的请求路径不要再接它**，否则同一个问题又会由两个"脑"分别作答。

共同约定：

- **有副作用的工具默认不暴露**，需要时显式开启；产生副作用前必须显式确认。
- **调用方身份不从模型来**：患者标识由调用方注入执行体，不在工具参数里，模型无法伪造。
- **轮次与证据都有上界**：工具循环轮次有硬上限，累积的证据条数也有上限。

### 挂号：模型只提议，写操作只由服务端执行

工具面与写入口是分开的，边界很清楚：

| 谁 | 能做什么 | 走哪条路 |
|---|---|---|
| 模型 | `list_departments` / `get_availability` / `booking_window` / `my_appointments`，外加**只读**的 `propose_booking`（产出一张待确认单，不占号） | 工具循环 |
| 患者 | **点确认**才真的取号；点退号才真的退号 | `POST /consult/booking/confirm`、`POST /consult/booking/cancel` |
| 前端 | 渲染服务端给的卡片 | `pending_action`（`/consult` 与 `/chat` 都有）；`/consult` 的响应还带 `appointments` |

- `book_appointment` 仍然注册在册，但标着 `side_effect=True`：工具循环没有 `confirm` 回调，
  所以它**默认不交给模型**，只有明确知道自己在做什么的调用方（MCP 加 `--allow-side-effects`）
  才拿得到。
- **确认请求只带 `proposal_id`**：科室、日期、时段、挂号费都取自服务端那张单子。前端若能回传
  这些字段，界面就成了价格与科室的真相源。
- 待确认单**进程内、一次性消费、15 分钟过期**（`domains/clinic/pending.py`）。业务失败返回
  **409 + 一句人话**（单子过期 / 号被占满 / 停诊），参数不合法由 pydantic 拦成 422。
- `/consult` 与 `/chat` 是**同一套**：都由模型提议、由前端卡片上的按钮触发同一个确认端点，
  没有"用户这句话里有没有挂号两个字"这类基于关键词的确认回调。

## 七、医疗产品层（`clinical/`）

`clinic` 域的**判断权全部在大模型**，其余组件围绕这件事分成三层：证据层给线索、
判断层下结论、约束层核对结论。在此之上还有第三层安全机制——确定性安全门（纯代码，
见「三层防护」一节）。各层的边界是这一节的主线。

```
证据层
  reference.py        参考标准面板的通用形状：FactSet / render() / to_payload()
  evidence.py         证据装配：检索片段、红线信号（含三维明细）、分诊候选、链路问题
  triage.py           检索式分诊：粗排 → 精排 → 科室投票，叠加科室补全表
  domains/clinic/reference.py  把域资产装成面板（症状词表、科室票数、科室表、号源事实）
判断层
  大模型              是否急症、挂哪个科、给不给检查/用药——唯一的判断者
  prompts/            它拿到的系统提示（三层防护的指令 + 硬性条款 R1–R6 + 输出契约）
约束层
  verify.py           拿同一份事实集校验模型的每一处输出（block / strip / warn）
  safety.py           确定性安全门：三条不变量 + 审计留档 + 兜底追问
  contracts.py        输出契约，以及 R3 的执行（无依据的检查/用药建议真的丢掉）
  runtime.py          **装配入口**：检索后端 + 域工具 + 工具循环 + 管线（产品与评测共用）
  pipeline.py         接线：装配面板 → 工具循环 → 校验 → 三级处置 → 安全门 → 落库
  intake.py           多轮采问：槽位采集与"最多问几次"的收敛
  reasoning.py        不带工具的一条判断路线（评测的单发臂直接用它；问诊管线不调用它）
  persistence.py      患者 / 就诊 / 消息 / 挂号关联（Postgres `clinical` schema）
```

号源与挂号工具不在这一层，而在域包 `domains/clinic/` 里（`provider.py` 是契约、
`pg_provider.py` 是 Postgres 实现、`pending.py` 是待确认单、`tools.py` 是工具面）。

**装配只有一处**（`runtime.py` 的 `build_clinical_assembly`）：`/consult` 与评测的
工具循环臂都调它。装配的每一件依赖都是注入的（检索器、号源服务、待确认单、就诊记录落点、
面板建造器、审计落点），所以产品注入真实实现、评测注入替身，而**代码路径完全一致**。
两边各写一遍装配的后果不是报错，而是"评测在测一个产品不会走的形状"——分数看起来仍然合理，
偏差却没人发现。评测侧的三处差异是刻意的：号源用 `MockAppointmentProvider`、
不落就诊记录、不写审计文件。

**就诊记录与挂号关联**：患者 / 就诊 / 消息 / 挂号关联都落 Postgres 的 `clinical` schema。
挂号关联是**单向**的（就诊 → 号），权威状态在 `booking.appointments`；`GET /consult/encounters`
的每条记录带 `bookings`，用来回答"这次问诊最后挂了哪个科"。

### 证据层：规则资产只提供线索

急诊红线词表 + 三维门控、口语症状词表、语料症状键、症状→科室票数、检索式分诊、
科室补全表、号源事实——这些确定性资产都还在，也都还有用，但**一条结论都不下**。
它们被装配成一个 `FactSet`（「参考标准」面板）：`render()` 把它渲染成提示词里的一段，
`to_payload()` 给出可逐轮对账的结构化形状——**哪个入口真的把它交给了模型，见下表**。
`RiskGuard` 的关键词命中**不在判断链上**：
它不覆盖 `urgency`、不短路流程，只作为线索进面板。

**这份面板在两个入口上的读者不同，这是读代码时最容易看错的一处：**

| 入口 | 面板进模型的提示词吗 | 谁读它 |
|---|---|---|
| `/chat`（`agent/clinic_react.py`） | **进**：`facts.render()` 拼进同一条 system 消息（紧挨着本轮提问） | 模型据线索自己判断；结构化形状进响应里的 `reference` |
| `/consult`（`clinical/pipeline.py`） | **进，但只是线索版**：`render(defer_retrieval=True)` 拼在系统提示之后，**不含预取的知识条目** | 模型据线索决定要不要检索；同一份完整事实再交给**约束层**（`verify.py`）核对输出，并进响应里的 `reference` 留档 |

两条路径喂给模型的那一份**只是线索**：`/consult` 递进去时会先把 `build_evidence` 预取的
知识条目清空（`clue_evidence`），否则"模型自己决定要不要检索"这条取舍就作废了——面板里的
知识依据是**它自己取回的**那批片段。规则资产（红线三维、症状归一、科室票数）不进任何
短路分支，只作为线索出现。

校验用的那一份事实与响应里的 `reference` 仍然是**循环之后**装配的完整版（那时才知道模型
检索到了什么，知识依据就是它取回的那些片段；红线线索与分诊候选则由管线预取的那一份补进来）。
`/chat` 没有这一层差别：它一次装配，同一份事实既递给模型也用于校验。
无论哪条路径，**校验依据与面板都是同一份事实**，不会出现"依据里有、校验时不算"这种
最坑人的不一致。

面板由六块内容组成，每一块都写明"这是线索、不是结论"：

| 块 | 面板里的写法 | 为什么这么写 |
|---|---|---|
| 急诊线索 | `一、急诊线索（关键词表 + 三维门控；**不构成急症结论**）`：命中的词 + 断言 / 经验者 / 时间性三维取值 + 门控结论 + **逐条三维明细**（最多 6 条） | 「我老公胸痛」「去年胸痛」为什么不触发，只有明细说得清——那正是模型最需要的解释。没命中就如实写"无" |
| 症状归一 | `二、症状归一线索`：患者原话词 → 标准词 → 它展开出的语料键（含是否已否定） | 三段都要留：只给首尾会写成"低烧 → 术后发热"这种错的关系，而"低烧 → 发热 → 术后发热…"才是能据以判断的形状 |
| 科室候选 | `三、科室候选线索（规则票数，**只是候选**）`：候选科室 + **票数与来源**，并给出可挂号科室清单 | 让模型看得见"这条线索是怎么来的"；票数高不等于结论对，它可能是被一个宽泛症状刷上去的 |
| 知识依据 | `【知识依据｜只能据此给检查与用药建议】`：`[K#]` 编号的命中片段 + 该片段所在小节全文；一条都没有时明写"本次**没有检索到任何资料**"。同一块里还会带 `【分诊信号｜仅供参考】` 候选与 `【检索链路问题】` | 这是唯一能支撑检查/用药建议的东西。检索为空必须明写，不能整段省略；检索链路出过问题也要让模型知道"这次依据不全" |
| 业务事实 | `五、业务事实`：号源余量、挂号费，以及**本轮服务端实际执行过的动作**；没有已确认的挂号/退号时明写"本轮服务端**没有**任何已确认的挂号/退号动作" | 动作幻觉最直接的解毒剂：模型看到空白会按对话语气补一句"已为您挂上"，看到这句明确的否定才有可对照的事实 |
| 线索装配问题 | `六、线索装配问题（这些线索这次不可用）`（只在装配出问题时出现） | 区分"没有信号"与"没查"——后者是系统故障，模型据此该更谨慎 |

**只写"无"、不整段省略**是有意的：面板空了会让模型以为"没有信号"与"没查"是同一件事，
而它们完全不同。

### 判断层：大模型是唯一判断者

是否急症、挂哪个科、给不给检查/用药建议，全部由模型给出，并要求它输出可审计的依据：
`red_flags` 的每一条都要写清是什么病症、严重到什么程度、凭什么这么判
（`contracts.RedFlag` 把 `condition` / `severity` / `why` / `angle` 都设成必填）。编排层
**不覆盖**模型给出的 `urgency`。

### 三层防护：判断权归模型，安全靠纵深

把判断交给模型之后，风险从"规则太笨"换成了"模型漏了 / 模型编了"。这两类风险用**三层
互不替代**的机制来压：任何一层被单独拿掉，另外两层都补不上它的洞。

| 层 | 在哪 | 负责什么 | 不负责什么 |
|---|---|---|---|
| **L1 语义理解** | 大模型（`prompts/system.md` R1） | **多角度**识别危险信号：`症状性质` / `组合共现` / `时间过程` / `严重度` / `高危人群` / `情境诱因`；每条给出 `likelihood` 与排除依据 | 不保证不漏 —— 所以需要另外两层 |
| **L2 主动问诊** | 大模型（R5）+ 契约（`contracts.validate_against`） | 没排除的危险信号必须问清"能区分要急救 / 不用急救"的那一个问题；低置信必须交代信息缺口 | 不负责安全动作的兜底 |
| **L3 确定性安全门** | **纯代码**（`clinical/safety.py`） | 三条不变量，模型说什么都不例外（见下） | 不做医学判断、不识别新病症 |

三层的衔接处有两条机械判据，都是"缺省值不许把安全问题抹掉"：

- `unresolved_signals()`：`ruled_out`，或"`unlikely` **且写清了排除依据**"才算排除；
  其余（含 `unlikely` 却没写依据）一律按未排除处理；
- `requires_emergency()`：`likely` / `very_likely`，或 `severity=critical`（**哪怕只是
  `possible`**）⇒ 这一轮必须判成 `emergency`。反过来，`severe + possible` 允许不判急症
  ——那正是 L2 要接住的情形：先进去问清那一个问题，而不是硬给结论。

### 约束层：拿同一份事实核对模型的每一处输出

最典型的风险形态是**动作幻觉**：服务端根本没挂上号，模型却写"已为您挂上，凭据号
XXXXXXXX"——这对患者是不可挽回的误导，他会以为号已到手。`clinical/verify.py` 拿面板
那一份事实逐项核对，违规分三级：

| 级别 | 含义 | 判据（`kind`） | 处置 |
|---|---|---|---|
| `block` | 内容不得让患者看到 | 动作幻觉（`fabricated_booking` / `fabricated_cancellation`）、编造凭据号（`unknown_ticket`）、**承诺了待确认单却没调 `propose_booking`**（`promised_booking_without_proposal`）、检索为空却给医学内容（`medical_without_evidence`） | 带违规原因**重生成一次**；仍违规则整段换成服务端拼的事实回答 |
| `strip` | 内容里**某一条**不合法 | 编造依据编号（`fabricated_evidence`）、科室未接地（`department_not_grounded`）、**事务性需求里多余的医学内容**（`medical_content_not_requested`） | 丢掉那一条（科室/建议），其余照常给患者 |
| `warn` | 需要留痕，但不该拦 | 未解释的红线线索（`red_line_unexplained`）、服务端没给过的金额（`unknown_amount`） | 只记进 `contract_violations`，不拦不改 |

`block` 与 `strip` 的区别是刻意的：一条编造的科室不该让整段回答消失，而"已挂上"这种
动作幻觉必须让整段回答消失——前者是信息不全，后者是误导行为。

**需求类型（`intent`）只收紧、不放宽。** 契约里新增了 `intent: medical | booking | admin`，
让模型先判断这一轮用户要什么：`booking`（挂号、查号源、退号）与 `admin`（流程、放号时间、
就诊记录）**不需要专业资料支撑**，所以这两类需求下若仍输出 `differentials` / `exams` /
`medications`，按 `strip` 删掉即可（证据其实是齐的，拦整轮只会把"今天还有号"这类有用的话
一起丢掉）。反过来**绕不过去**：没有知识证据时一律按 `medical_without_evidence` 走 `block`，
与 `intent` 写成什么无关——"不需要专业支撑"省掉的是**多余的医学内容**，不是**依据**。
缺省值是 `medical`（最保守）：模型没给、给错或解析失败，行为与以前完全一致。

三级处置（`pipeline.py` 的 `_tool_loop_turn`、`agent/clinic_react.py` 的 `turn()`）：

1. 有 `block` 级违规 ⇒ **带违规原因重生成一次**（多花一次循环，比给患者一句编造的话便宜得多）；
2. 重生成仍违规则 ⇒ **不展示模型那段散文**，改由 `facts_only_answer()` 拼一段只含事实的回答；
   这段回答会带上服务端**已经握有**的科室线索（科室补全表）与号源读数（业务库）——它们不依赖检索，
   没有理由因为模型越界而一起消失；拼不出任何事实时才只回 `NO_EVIDENCE_ANSWER`——宁可少说，不可编；
   这一轮的 `action` 是 **`answer` 而不是 `error`**：服务端确实给出了回答，它只是降级形态；
3. **历次尝试**的违规全部进 `contract_violations` 随响应回去。它是"模型有没有在编造"的
   唯一可观测读数，只写日志等于没人看得见——第一轮确实越界了，不能因为第二轮回正就当没发生。

**顺序有讲究：先校验、再执行契约、最后过安全门。** `contracts.enforce` 会把没有依据的
检查/用药建议**删掉**（R3：检索不到就不给）；若先跑它，"检索为空却给了医学内容"这条检查
就看不到任何异常（字段已被清空），而**散文里的那句话照样会送到患者眼前**。校验要看到的是
模型**原始**的输出。安全门排在最后，因为它看的是"患者最终会看到的那段话"。

**一条安全例外**：建议就医 / 拨打 120 属于**安全动作**，不是事实断言，所以检索为空时照样
要给（`NO_EVIDENCE_ANSWER` 的尾句）。否则"检索不到就说不知道"会把该报警的急症一起拦下
——那是拿安全换整洁。真正被禁的是"你可能是 X 病"这类**事实断言**。

**不向模型要"自我声明"**：校验所需的信息全部由服务端从已有产物推导（契约对象的字段 +
给患者那段散文），不新增"请声明你有没有编造"这类字段——自我声明正是模型可以撒谎的地方，
而"它引用了哪些编号""它给了哪些科室""它有没有给出医学内容"服务端自己就算得出来。
唯一的例外是 `confidence`（自报置信度）：它只用于"低置信必须交代信息缺口"这条行为约束
与校准统计，**不当作概率、也不进任何阈值**，可信度由校准报表单独衡量。

两条路径都接这一层，只是**能验什么**不同：`/consult` 有结构化契约，能验满五项；
`/chat` 的输出是一段自由文本（`verify_prose()`），只做**能被事实锚定**的那几项——动作幻觉、
凭据号、金额、红线未解释。散文里没有 `evidence_ids` / `departments` 字段，所以"编造依据
编号""科室未接地""无依据却给医学内容"这三项**不在散文上假装能验**：从文本里"找科室名"
会把"不是心内科的问题"误判成科室建议。两条路径的 `contract_violations` 因此是同一形状、
同一口径（历次尝试全部留档），不是同一套判据。

### 确定性安全门：三条不变量

`clinical/safety.py` 的 `INVARIANTS` 是这几条底线的**唯一来源**，每条都声明：理由、
触发后的处置动作、实现位置、以及它在哪几条入口上成立。

| id | 触发条件 | 处置 | 入口 |
|---|---|---|---|
| `no_medical_advice_without_evidence` | 检索为空却给了方向/检查/用药建议 | 整段换成只含事实的回答 | `/consult` |
| `no_fabricated_booking_action` | 声称了服务端没执行过的挂号/退号/凭据号 | 同上 | `/consult` + `/chat` |
| `emergency_judgment_requires_directive` | 判了急症（或存在 `critical`/`likely` 的危险信号）而正文里没有可执行急救动作 | **追加**固定指引，并把这一轮的动作升级为 `emergency` | `/consult` |

第三条与另外两条方向相反：它**补内容**而不是删内容。理由是安全性只能往上加——
模型少写一句"打 120"不该让患者失去这句，所以判据只认**想去哪**（120 / 急诊 / 救护车 /
立刻就医），不认"要注意"这类没有动作的措辞。

**为什么只有三条**：它们是**能被事实锚定**的（有没有依据、服务端有没有执行过那个动作、
正文里有没有急救动作），不需要医学知识。凡是需要医学判断的一律留在 L1/L2 交给模型——
把需要判断的东西写成 `if` 语句，只会得到一个看起来安全、实际没人负责的假门。

前两条由 `verify.py` 检出、在安全门里**按同一套口径登记**（判定与执行写在两处会静默分歧，
所以留档必须在一个地方收口）；`verify.py` 里 `warn` 级的类别（金额、红线未解释）**不进安全门**：
它们只是回答质量问题，混进来会让"安全门触发次数"这个读数失真。

### 不确定性量化

不只是"让模型谦虚一点"，而是三条能机械核对的要求 + 两个可看的读数：

- `red_flags[].likelihood`：这条信号被排除到什么程度。它决定 `urgency` 与要不要追问；
- `confidence` / `information_gaps`：自报置信度低于 `CONFIDENCE_FLOOR`（0.6）时**必须**
  写清还缺什么信息（契约层核对）；缺 `confidence` 本身也记一条；
- `unresolved_signals()` 非空且不是急症 ⇒ 必须有追问（L2）；
- **校准**（`evaluation/calibration.py`）：把（自报置信度，是否判对）算成 Brier 分数与
  可靠性分箱，回答"它说 0.8 的时候真的对了几成"。**只报告，不上门限**：小样本上校准数字
  波动很大，拿它卡门禁等于用噪声判生死；样本量不足时报表自己会写明。

### 记忆与持久化（三层，只有一层刻意不落库）

| 层 | 内容 | 落在 | 重启后 |
|---|---|---|---|
| **会话状态**（实体记忆） | 采问槽位 `IntakeState.filled/asked` + 最近 `MAX_HISTORY_TURNS` 轮对话上文（assistant 侧存**契约 JSON**，不是散文） | **Postgres `clinical.sessions`**（`session_id` 主键、upsert 覆盖，`created_at` 只在首插时生效）+ 进程内一份缓存 | 还在 |
| **长期记录** | `patients` / `encounters`（**每轮一条**，主诉 + 结论 JSON）/ `messages`（role+text）/ `bookings`（就诊↔号单向投影） | **Postgres `clinical`** | 还在 |
| 待确认挂号单 | 科室 / 日期 / 时段 / 费用 / 余量 | **进程内** `PendingBookings`（一次性、15 分钟） | 丢——它是提议，不是记录 |

写路径：每轮结束**写回一次**会话行（`ConsultRuntime._persist_session` → `save_session`），
读路径在缓存未命中时**从库里捞**（`_load_session`）。两条都是"尽力而为"：
读不出来按新会话处理、写不进去只留 warning——会话状态丢了只是"要重新问一遍"，
不该让这一轮问诊失败。`/consult/reset` 同时清内存与库里那一行，否则下一次请求会把旧槽位捞回来。

为什么实体记忆必须落库：进程内字典在**重启 / 换副本 / 多 worker** 时就没了，患者会发现
"刚说过的话系统不记得了"，而状态端点上又看不出这件事。落库之后它与就诊记录一起具备
"跨重启有效"的性质；数据库不可达时如实降级为 `in-process`（`/consult/status` 的
`session_store` 与 `persistence_backend` 两处会一起说出来）。

⚠ 待确认单**刻意不落库**（见 `DECISIONS.md` 第 15 条）：它是一次性提议，落库就要配套
过期清扫任务，而收益只是"重启后还能点 15 分钟前那张单子"——那件事对患者没有价值。

### 一次问诊的形状

```
患者发言
  │
  ├─ 采问：补齐关键信息；信息不足则追问（有次数上限，不会无限问）
  │
  ├─ 装配参考标准面板：急诊线索（含三维明细）· 症状归一 · 科室候选 · 知识依据 · 业务事实
  │
  ├─ 取证：模型调用工具（检索知识卡片、核对引用…）
  │        返回的知识片段由程序编号 K1、K2…，模型引用编号
  │
  ├─ L1 判断：模型**多角度**识别危险信号，输出结构化结论（契约化）
  │        urgency · red_flags（含 angle / likelihood / discriminator）
  │        · departments · differentials · exams · medications
  │        · patient_summary · followup_questions · information_gaps · confidence
  │
  ├─ L2 主动问诊：没排除的危险信号必须问清"能区分要急救 / 不用急救"的那一个问题
  │        模型没问 ⇒ 服务端用它写的 discriminator 补一句（没有就按病症生成）
  │
  ├─ 校验：拿同一份事实集验它的每一处输出
  │        block 级 ⇒ 带原因重生成一次；仍违规 ⇒ 那段散文不上屏，换成只含事实的回答
  │        strip 级 ⇒ 丢掉那一条；warn 级 ⇒ 只留痕
  │
  ├─ 执行契约：没有依据的检查/用药建议真的丢掉（R3）
  │
  ├─ L3 安全门：三条不变量（判了急症没给急救动作 ⇒ **补**上；触发的那几条写进审计）
  │
  └─ 应答：`patient_summary`（对话体）+ 急诊提示（如需）+ 落库 + 审计留档
```

**无判断者就没有结论**（文案的唯一来源是 `llm_status.py`）：没配密钥回
「未连接大模型，请连接大模型后重试。」；配了但这次调用失败（超时 / 限流 / 输出不可解析 /
预算用尽）回「大模型调用失败，请稍后重试。」。两句刻意不合并——把"连了但失败"说成
"未连接大模型"，会让运维去翻一个其实配好的密钥。

**任何兜底内容都不产出**：模型失败时 `assessment` 留空（不按现有证据凑一个有限结论），
`Answerer.answer()` 把 `citations` 清空、不把检索结果当成回答交付，`/ask` 没密钥时
**在检索之前**就回那句话。唯一的例外是 L3 那条**补**急救动作的不变量——它加的是安全动作，
不是医学结论（见「三层防护」）。

治理（安全资产变更控制、审计、评测档案、已知缺口）见 [`GOVERNANCE.md`](GOVERNANCE.md)。


## 八、可观测与运维

- `GET /metrics`：Prometheus 指标，含按端点的请求数与耗时、检索各路耗时、LLM 花费与预算。
- `GET /healthz`：存活 + 当前域的块数，外加 `store`（实际生效的存储后端类名）与
  `store_fallback`（降级原因）。**索引不可用 / 索引为空都不算存活失败**：返回 200、
  `ok=true`、`n_chunks=0`——探针报 red 会触发重启，而重启解决不了"Postgres 没起"。
- `GET /consult/status`：会话数、待确认挂号单数、号源后端（`booking_backend`）、
  就诊记录后端与各表行数、**安全模型自述与最近触发记录**（`safety_model` /
  `safety_invariants` / `safety_audit_recent` 与审计日志路径）——**不触发管线装配**，
  所以可以随便探。"没触发"与"没在跑"要能分开，所以这里同时给出不变量条数与审计条数。
- `POST /consult` 的响应带 `reference`（这一轮的事实集，即面板的结构化形状）、
  `contract_violations`（这一轮被约束层拦下的**逐条明细**）与 `safety`（这一轮安全门
  执行了哪几条**底线**：不变量 id + 处置动作）。三者**必须成对留档**：只有同时留下
  "它手上有什么依据""它哪里越界了""程序因此做了什么"，事后才能回答"这次是依据不够，
  还是模型没守规矩"。`/chat` 的 `message` 事件带同一组字段、同一口径。
- 安全审计：每次不变量被触发，`data/index/safety_audit.jsonl` 追加一行（`ts` / `domain` /
  `invariant` / `action` / `detail` / `trace_id`）。**刻意不记患者原话**——临床文本在
  `clinical` schema 里，有自己的访问控制，审计再抄一份只会扩大泄露面；需要细节时按
  `trace_id`（= `encounter_id`）去临床库取。写失败不影响这一轮应答，但会记 warning。
- 安全门计数：`kubedocs_safety_invariant_fired_total{invariant,domain}`（Prometheus）。
  审计文件回答"发生了什么"，计数回答"最近是不是变多了"；两者在同一个收口点
  （`clinical/safety.py` 的 `append_audit`）产出，避免"记了日志没计数"。
- 长期监听：`scripts/monitor_clinic.py` 定期跑一轮评测（**复用** `scripts/eval_clinic.py`
  的 `main()`），把结果与最近几轮比对。指标变化只提示（`note`），安全不变量触发、
  运行没跑成、有题目没拿到判断才让退出码变 1（`alert`）。趋势记录落在
  `data/eval/clinic_trend.jsonl`，与治理档案同一轮写出。见 [`GOVERNANCE.md`](GOVERNANCE.md)。
- 花费：所有模型调用共用一本日预算账本，账本按日累计落在 `data/index/llm_spend.json`。
