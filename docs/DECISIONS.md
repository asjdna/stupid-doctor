# 设计决策

记录几个影响面较大的选择，以及它们带来的取舍。每条给出**结论**和**理由**，
便于后来者判断"要不要沿用"。

## 1. 技术选型

| 需求 | 选择 | 理由 |
|---|---|---|
| Web 框架 | FastAPI + uvicorn | 类型化请求/响应与自动文档；同步端点跑在线程池，适合本项目"检索重、并发低"的形态 |
| 模型接入 | LiteLLM | 多供应商路由、重试、回退与成本统计都交给它，自研是重复劳动；换供应商只改一个模型名 |
| 嵌入 | sentence-transformers + `bge-small-*` | 本地推理、无需外网、CPU 可用；中英文各一个小模型，384/512 维足够本项目语料规模 |
| 契约 | pydantic v2 | 输出契约需要严格校验（`extra="forbid"`）与清晰的错误信息 |
| Agent 编排 | 工具循环（function calling）+ LangGraph | 请求路径用工具循环：模型自己决定调哪些工具取证；LangGraph 图带耐久状态与真中断（`interrupt`），保留为"规则判断 vs 模型判断"的对照臂 |
| 工具对外 | HTTP `/tools` | 一处注册、两处消费（端点自省 + Agent 工具循环），不必为每个客户端写适配层 |
| 存储默认 | pgvector（Postgres + pgvector） | 向量与全文同库、索引跨重启跨副本共享；生产形态与本地形态是同一个后端，不必"上了生产再换一套" |

**关键取舍**：默认后端要的是"**正确性与可运维性**"，不是极限延迟。
本机开发与生产用同一个后端，索引位置不随环境漂移；离线场景有显式的本地回退（见第 5 条）。

## 2. 先跑通业务逻辑，再做优化

先把一条完整链路（摄取 → 检索 → 回答 → 评测）跑通，再谈调参与换组件。
理由很直接：没有端到端链路时，任何局部优化的收益都无法验证。

对应到工程上的表现：**每个阶段都留下可复现的度量**，而不是凭感觉调参。

## 3. 双域平台，而不是两个项目

`k8s_docs` 与 `clinic` 共用同一套底座（存储、检索、Agent、观测、评测），差异全部收在域包里。

**好处**：底座的能力（混合检索、引用核对、评测闸门、可观测）一次实现，两处受益；
新域只写"语料 + 配置 + 工具"。

**代价**：域包必须**严格隔离**——各自的索引目录、存储 schema、向量维度与归一化器。
一旦混用，两套向量会进同一个矩阵且不会报错，属于必须从设计上避免的问题。

## 4. 医疗语料不入库

医疗语料体积大，且受上游许可约束，因此**不被仓库携带**：仓库只带代码、脚本与评测用例。
需要用的人按 README 的说明按需获取或重建；索引同样是派生物，可随时重建。

**衍生约束**：**没有语料时，各条流程仍必须能完整跑通**——症状归一化与急诊红线由域内词典
与三维门控驱动，不依赖知识卡片；判断本身由大模型做出，缺语料只会让它**少一份线索**
（科室候选票数与检索依据），而面板会如实写明"这份线索这次不可用"。
知识卡片提供的是"为什么这样建议"的接地依据，以及症状→科室票数。

许可与来源见 [NOTICE.md](../NOTICE.md)。

## 5. 向量后端可替换，默认 pgvector，离线时可见地降级

| 后端 | 适用 |
|---|---|
| `pgvector`（默认） | Postgres + pgvector HNSW：一库同时承担全文与向量、索引跨重启跨副本共享 |
| `sqlite-vec` | 离线回退：零外部进程、零镜像、零网络；SQLite + sqlite-vec 向量索引 |
| `sqlite` | numpy 暴力内积 + `.npy` 侧车矩阵：最小依赖，兼作性能对照 |

**为什么默认是 pgvector**：索引是要被**多进程读**的东西——HTTP 服务、CLI、评测脚本常常同时在跑，
而"索引在谁的进程里"不该决定谁能读到它。把索引放进 Postgres 之后，重启、多副本、备份都走数据库
既有机制，也省掉了"本机一套、容器另一套"的双份运维。代价是默认需要 Postgres。

**两条失败路径刻意不同**：

- **非法取值直接报错**，绝不静默回退。回退成默认后端会让"我明明切到 pgvector 了，为什么数据
  还是旧的"变成一个没有任何日志的谜。
- **数据库不可达降级为 `sqlite-vec`**，原因写在返回对象的 `fallback_reason` 上。理由很直接：
  一台没装 Docker 的机器上连 `ingest` 都起不来，等于把本地开发锁死在基础设施上。
  传 `allow_local_fallback=False` 可以让它原样抛错，留给"基础设施没起就该响亮失败"的调用方。

**降级必须可见，因为它有代价**：两个后端的索引存在**不同位置**，降级期间建的索引在 Postgres
恢复后是**看不见**的。所以 `fallback_reason` 不是只写日志，而是被 `/healthz` 的
`store_fallback`、CLI `stats` 的「存储后端 X（配置 Y）」与 `⚠ 已降级：…` 读出来。
换句话说：降级允许发生，但不允许**悄悄地**发生。

## 6. 回答必须带引用，且引用可核对

生成层要求回答里的 `[n]` 指向真实提供的片段；越界引用会被剥离并记入诊断，
"一个引用都没有"同样会被标记。另提供 `check_citations` 工具，供模型自查。

**理由**：一个能追溯到出处、也能被指出"没有出处"的回答，比一个无法核对的流畅回答更有用。

## 7. 急诊判断交给大模型，规则资产只提供线索

- 判断依据是**病症 + 严重程度**，并要求输出可审计的依据（是什么病症、严重到什么程度、凭什么）。
- 急诊红线词表 + 三维门控、口语症状词表、症状→科室票数**都不下结论**：它们被装进
  参考标准面板，由模型自己判断（见第 18 条）。
- **契约层守住自相矛盾**：判出 `red_flags` 却把 `urgency` 写成非 `emergency`，会被记进
  这一轮的 `problems`。
- **急重症信息优先展示**：`red_flags` 不因"依据缺失"或"格式问题"被删除。

**取舍**：判断质量取决于模型——词表覆盖不到的说法，模型可能判得更好；而模型判漏的那一次，
没有确定性兜底。这个不对称是有意的：换来的是"同一个问题只有一个判断者"，
以及规则线索仍然完整地摆在判断者面前（包括"系统看到了这个词、但认为不该作为本人当前
主诉上报"的三维明细）。

## 8. 检查与用药建议只能来自检索到的资料

**检索不到就不给，不用模型的通用知识补足。** 这条由契约层强制执行：
没有依据、或引用了不存在依据的条目会被**丢弃**，而不是照发给用户。

**理由**：在医疗场景里，"不说"比"说一个没有本地资料支撑的结论"安全得多。
代价是覆盖面变小——这是有意选择。

**执行有顺序**：这条约束由 `contracts.enforce` 真的丢掉条目，而校验（`verify.py`）
必须**先**跑完——理由见第 20 条。

## 9. 追问与科室/用药的呈现节奏

- 信息不足时追问，但**有次数上限**，不会无限问。
- 主回答讲"现在该怎么办 → 可能方向排序（每项说明理由）→ 检查建议 → 何时必须立刻去医院"。
- **科室建议与用药建议不主动铺开**，在结尾用一句话邀请用户来问。
  理由：一次全倒出来会淹掉真正紧急的那句话；而急重症情形下这两项必须当场说清。

## 10. 有副作用的操作必须显式确认

挂号会占用号源，因此：

- 有副作用的工具**默认不暴露**给模型；
- 产生副作用前必须得到用户显式确认，未确认绝不执行；
- 这一约束由工具注册表与编排层统一保证（`ToolSpec.side_effect` + 调用前的确认），
  新增工具时按同一约定声明即可。

**进一步的选择：模型只提议，写操作只由服务端执行。** 确认若是"模型再调一次带 `confirm=true`
的工具"，那仍然是模型在执行写操作，患者点的那个"确认"只是它自己声明收到过。所以挂号被拆成两半：

- 模型侧只有**只读**的 `propose_booking`：验证科室/日期/时段真有号，产出一张待确认单，
  号源一个都不动；
- 真正写库的只有两个 HTTP 端点（`POST /consult/booking/confirm`、`POST /consult/booking/cancel`），
  由患者在界面上点按钮触发；
- **确认请求只带 `proposal_id`**：科室、日期、时段、挂号费都取自服务端那张单子。
  如果让前端回传这些字段，界面就成了价格与科室的真相源——改一个数字就能少付几块钱，
  或者重放别人的请求；
- `book_appointment` 仍然保留但标着 `side_effect=True`，工具循环没有 `confirm` 回调，
  因此默认不交给模型；只有明确知道自己在做什么的调用方（MCP 加 `--allow-side-effects`）
  才拿得到。

`/chat` 与 `/consult` 走的是同一套：都由模型提议、由前端卡片上的按钮触发同一个确认端点，
没有"用户这句话里有没有挂号两个字"这类基于关键词的确认回调。

## 11. 存储与检索的失败要显式降级

任一路检索失败（嵌入不可用、存储异常）都退化为可用的一路，并**在结果里记录原因**；
索引不可用不算存活失败，`/healthz` 仍返回 200，用 `n_chunks=0` 与 `store_fallback`
如实说明发生了什么。

**理由**：把失败原因暴露出来，比返回一个空结果或把服务判为不健康更容易排查。

## 12. 花费有上限，且账本可查

所有模型调用共用一本按日累计的预算账本；当日额度用尽后调用会被拒绝而不是静默继续。
账本落在 `data/index/llm_spend.json`，可按日核对。工具循环的每一次调用同样计费。

## 13. 切块切两层，尺寸是 300 / 60 / 3000

一个块同时承担两件事时，两件事都会被做坏：块小则检索精确但模型读不到前后文，
块大则语境完整但向量被整节平均掉、任何一句都不再突出。所以切成两层，
**检索用子块、生成用父块**（见 [`ARCHITECTURE.md`](ARCHITECTURE.md) 的检索一节）。

三个数各自回答一个问题，**不要互相推导**：

| 参数 | 值 | 它回答的问题 |
|---|---|---|
| `CHILD_TARGET_CHARS` | 300 | 检索单位该多大？小到能精确命中一个具体说法（一句参数说明、一行报错含义），而不是整节"泛泛相关" |
| `CHILD_OVERLAP_CHARS` | 60 | 一句话正好被切在边界上时留多少缓冲？子块本身就短，重叠按比例取；太大等于 300 字里一半是重复 |
| `PARENT_MAX_CHARS` | 3000 | 上下文单位的上限：小节超过它就按段落边界拆成多个父块，保证任何一个父块都能整段放进模型上下文 |

配套的两条规则同样是刻意的：

- **`chunk_id` 形状不变**（`<doc_id>::<四位序号>`）：它是增量摄取定位行的键，换形状等于让已有索引
  的行全部对不上，而它们本来就是同一批内容。父块另起一套 id（`<doc_id>::p<四位序号>`）。
- **短碎片只在同一个父块内合并**：跨父块合并会把上一节的残句接到下一节的引用下，
  而引用说的还是上一节。
- **`top_k` 是去重之后的条数**（同一篇文档最多 `KUBEDOCS_MAX_CHUNKS_PER_DOC` 条，默认 2）。
  块变小之后，同一节的兄弟块会一起挤进前几名：实测 50 条 gold 上 `top_k=10` 里平均只有
  **5.38 篇不同文档**、最少的一次 10 条来自 2 篇。去重后 hit@10 从 0.78 升到 0.86。
  这不是"为了指标"：hit@k 按文档算，而"返回 10 条结果"在文档问答里本来就该是"10 处不同出处"。
  上限与"进模型上下文时同一文档最多收 2 段"**共用同一个配置**——同一条约束不该有两个数。

## 14. 卡片语料不做两层

`clinic` 的知识卡片**父块与子块同文**，保持一层。

理由：卡片是**按原子知识单元撰写的**（一张卡讲一个症状或一个处置），它已经是"检索单位"与
"语境单位"的合体。再按段落切成"症状 / 处置 / 红旗"三块，命中的会是半张卡——
`症状：胸痛` 这种片段单独拿出来，既不足以判断该挂哪个科，也会让引用指向一段读不出结论的文字。

代价是卡片语料的"父块"不提供额外语境。但父块行仍然照写，于是**读路径与文档语料完全一致**，
不需要"卡片走另一条分支"。

## 15. 待确认挂号单是一次性的、进程内的

`PendingBookings` 的三条性质都不是随手定的：

- **一次性消费**（`take()` 取出即作废）：双击确认、网络重试、刷新页面重放，都只会有一张单子生效。
  "重复提交变成两张号"在这里就被掐掉，不必指望下游的幂等键兜底。
- **15 分钟过期**（`DEFAULT_TTL_SECONDS`）：取值理由是"够患者读完并决定"，**不是安全边界**。
- **只在进程内存里**：重启进程后待确认单全部失效，患者重新说一句"帮我挂号"即可（提议是只读的，
  重来一次没有代价）。反过来，把单子落库就得配套一个过期清扫任务，而它的唯一作用是让
  "重启后还能点 15 分钟前那张单子"成立——那件事对患者没有价值。

参数留在服务端那张单子上，也是同一处的取舍：确认请求只带 `proposal_id`，前端与模型都改不动
科室、日期与费用。

## 16. 队列号按「科室 + 日期 + 时段」从 1 起

上午 1..N、下午也从 1 起——这是真实医院的叫号口径。

**`period` 必须同时出现在唯一约束与取号 SQL 两处**：只改一处的话，跨时段并发占号时两个事务
各自算 `MAX(queue_no)` 会拿到同一个号。上下午落在**不同的 schedule 行**上、互不阻塞，
所以这个错误不会自己暴露，只会在写入时撞约束。约束是
`UNIQUE(department, date, period, queue_no)`。

占号本身是**一个事务里的一句条件更新**（`UPDATE ... WHERE remaining > 0 AND NOT closed
RETURNING remaining`），不是"先 SELECT 再 UPDATE"：判定与扣减在同一句话里，所以不可能超卖。

**凭据号是 8 位大写字母数字，并且去掉了 `I` / `O` / `0` / `1`**：号要口头报给患者、也要印在
单子上，"到底是 I 还是一、是 O 还是零"是现场最常见的错。**假支付**：状态位保留
`pending_payment` / `paid`，但当前口径是"确认即视为已付"，所以取号直接落 `paid`、
`expires_at` 留空；`pending_payment` 是给后续"先占号再付、超时回收"留的位，
本仓库没有超时回收器。

## 17. 多格式语料的位置语义按格式定义，不统一成行号

把 PDF 的页码、表格的单元格区间、幻灯片的序号统一成"行号"会抹平语义——
搜到的第 3 行既不是第 3 页，也不是 `Sheet1` 的第 3 行，引用也就失去了可追溯性。
所以 `parse.py` 按格式分别定义位置：PDF 是 `p.7`、表格是 `Sheet1!A1:C20`、幻灯片是 `slide 3`，
标题型格式（md / html / docx）用标题路径。

位置作为**面包屑首段**进入引用（`[手册.pdf › p.7]`），因此不需要新增存储字段。
相应地有一条硬规则：**父块不跨位置**——跨页/跨表合并会把下一页的文字挂到上一页的引用下，
"引用可追溯"就成了假话。

配合同一组约束的还有三条：编码严格探测、绝不 `errors="ignore"` 静默丢字；
扫描件 PDF 点名跳过、绝不建空块；单文件失败不影响整批。理由都写在 `parse.py` 顶部。

## 18. 规则资产降级为「证据提供者」

仓库里有一批确定性资产：急诊红线词表 + 三维门控、口语症状词表、语料症状键、
症状→科室票数、检索式分诊、科室补全表、号源事实。它们的价值是**提供线索**，
不是**下判断**。所以它们被装配成一个 `FactSet`（「参考标准」面板），
而判断（是否急症、挂哪个科、给不给检查/用药）只由模型做出。

**面板在两个入口上都递给模型**，差别在**递的是哪一版**：`/chat` 把渲染好的面板拼进系统
提示，模型据线索判断；`/consult` 递的是**线索版**（`render(defer_retrieval=True)`：知识依据
留空，检索仍由模型自己调工具决定），规则资产同样以线索形式出现，不存在任何短路分支。
循环跑完之后，同一份完整 `FactSet` 由约束层（`verify.py`）拿去核对输出，并随响应以
`reference` 留档。两条路径的装配时机也因此不同（`/chat` 一次装配、既给模型也用于校验；
`/consult` 先装配线索版递进去、循环后再装配完整版用于校验与留档）。

**为什么不让规则参与判断**：只要规则能在某条路径上直接产出结论，同一个问题就有两个脑在答，
而且规则那个脑看不到患者的原话上下文——「我老公胸痛」与「我胸痛」在关键词层面一模一样。
三维门控（断言 / 经验者 / 时间性）能挡住一部分，但挡不住的部分要靠读原话，那是模型的活。
把判断统一到模型之后，"给患者的结论"与"面板上的线索"就能用**同一份事实**对齐。

**面板写法上的三条硬规定**（都在 `clinical/reference.py` 的模块文档里）：

1. 每条都写明"这不是结论"——面板本身不能变成第二个判断者；
2. 没命中要如实写"无"，不能整段省略——省略会让模型把"没有信号"读成"没查"；
3. 业务事实要写死"本轮发生过什么"，尤其是"本轮服务端**没有**任何已确认的挂号/退号动作"
   这句明确的否定。

**代价**：规则的确定性不再用来兜住模型的漏判。这一条被单独记在第 19 条里。

**确定性图（`agent/kernel.py` 的 `ClinicAgent`）因此退出请求路径**，只作为对照臂保留：
评测里拿它跑同一批问题，比较"规则判断 vs 模型判断"的差异——那正是这条改动最直接的证据。

## 19. 不留任何兜底：没有判断者就没有结论

模型不可用（没配密钥）或这一次调用失败（超时 / 限流 / 输出不可解析 / 预算用尽）时，
系统**不产出任何临床内容**：不拿检索结果冒充回答，不让规则轨顶替结论，不给保守话术。
只有两句文案，定义在 `src/kubedocs/llm_status.py`，两种情形刻意分开：

| 情形 | 文案 | 用户/运维要做的 |
|---|---|---|
| 压根没配密钥 | 「未连接大模型，请连接大模型后重试。」 | 去配密钥 |
| 配了但这次没成功 | 「大模型调用失败，请稍后重试。」 | 重试；运维去查网络/额度 |

**为什么合并是错的**：把"连了但失败"说成"未连接大模型"，会让运维去翻一个其实配好的密钥，
而真正的原因没有任何人看见。

落点（都在代码里可核对）：`ClinicalReasoner.reason()` 失败时返回 `assessment=None`；
`ClinicalPipeline` 用 `has_llm` 判定后只回 `NO_LLM_MESSAGE`，**不检索、不装配面板**；
`Answerer.answer()` 只回文案并清空 `citations`；`/ask` 没密钥时在检索之前就返回
（`n_hits=0`）；CLI `ask` 打这句话并以退出码 3 结束；`/chat` 不回退到确定性图。

**不受影响的入口**（它们不需要大模型）：`/search`、`ingest`、`stats`、`/healthz`、
`/metrics`、`domains`、`tools`，以及 MCP 工具——MCP 用的是客户端自己的模型，
服务端不替它调模型。

## 20. 先校验、再执行契约

一轮问诊里，模型输出要先过 `clinical/verify.py`（拿事实集核对），再过
`contracts.enforce`（把没有依据的检查/用药建议真的丢掉）。**顺序不能反。**

反过来的后果是具体的：`enforce` 会把无依据的条目从结构化字段里删掉，于是
"检索为空却给了医学内容"这条检查（`medical_without_evidence`）**看不到任何异常**——
字段已经空了；而模型写进 `patient_summary` 的那句话**照样会送到患者眼前**。
校验要看到的是模型的**原始**输出，所以它必须排在执行之前。

同一处还有一条纪律：**历次尝试的违规全部留档**。第一轮确实越界了，不能因为第二轮回正
就当没发生——"模型偶尔会编"正是这套架构最需要被观测到的东西。`/chat` 的散文路径
（`verify_prose()`）走同一条纪律：动作幻觉、凭据号这类能被事实锚定的检查照做，重生成后
回正的违规同样进 `contract_violations`。

## 21. 安全动作豁免依据要求

检索为空时，系统只允许回 `NO_EVIDENCE_ANSWER`。它的尾句是"如果症状持续或加重请及时就医；
出现胸痛、呼吸困难、意识不清等请立即拨打 120"——这句**必须给**，即使一条资料都没检索到。

理由：建议就医、拨打 120 属于**安全动作**，不是**事实断言**。事实断言（"你可能是 X 病"）
依然必须有检索依据；而安全动作没有依据问题，把它一起拦下去就是拿安全换整洁——
"检索不到就说不知道"会把该报警的急症也一起咽掉。所以 `verify.py` 的
`medical_without_evidence` 判据里把 `emergency` 排除在外，提示词 R6 也把这条写成了
唯一的安全例外。

## 22. 科室名要收掉口语后缀，且校验按同一套规则归一化

`normalize_department()` 会先查别名表，再试去掉口语后缀（`门诊` / `科室` / `科门诊`），
**只有去掉后确实命中**别名表或可挂号科室表时才采用；不认识的名字一律原样返回（把"某某门诊"
无条件截断会造出另一个不存在的科室名，那比原样返回更糟——原样返回至少能在报错信息里被看见）。

它有两个读者，必须用**同一套规则**：

1. **挂号**：模型与患者都会说"呼吸内科门诊""全科门诊"，而号源表里只有"呼吸内科""全科"。
   `BookingService.resolve_department()` 拿到的若是未归一化的名字，就会判定"不在可挂号科室里"
   并报错，整轮取号失败——而模型说的明明是同一个科。
2. **接地校验**：`verify.py` 的科室判据必须**归一化后**比较。拿原始字符串硬比会把
   "呼吸内科门诊"判成未接地（`department_not_grounded`）并从建议里剔除，患者能看到的那条
   正确建议就凭空消失了。

归一的**规则本身属于域知识**（clinic 的科室表与别名表），所以 `FactSet` 只收一个可调用
对象（`normalize_department`）、自己不实现规则，由 `domains/clinic/reference.py` 注入；
不注入时按原样比较，归一化函数抛异常时退回原值——宁可多报一条科室，也不要误删患者能看到的
建议。

## 23. 依据编号同时接受 `K#` 与索引真实 `chunk_id`

模型引用依据时两种写法都算数：我们自己分配的 `K1`、`K2`，以及索引里的真实 `chunk_id`
（形如 `disease/咳嗽::0000`）。`FactSet.evidence_ids()` 把两者并成一个集合。

**为什么必须接受后者**：`search_docs` 工具返回给模型的就是 `chunk_id`，模型很自然会照抄它
当"依据编号"写进 `evidence_ids`（实测如此）。只认 `K#` 会把一条**真实命中**判成
`fabricated_evidence`（编造依据）并丢掉整条建议——那是纯粹的误伤，而且看起来像模型在撒谎。
证据装配因此把索引真实 id 一并记进 `EvidenceItem.source_id`（`evidence.py` 与
`orchestration.py` 两个装配点都记），校验时两种写法都认。

## 24. 安全性靠三层防护与治理，不靠指标门限

**决定**：clinic 的安全机制是三层（L1 语义理解 / L2 主动问诊 / L3 确定性安全门，
见 `clinical/safety.py`），评测里的**指标一律不判通过/不通过**——包括危险信号召回。
唯一按内容卡 CI 的是 `scripts/check_governance.py`：安全资产哈希是否同步、
不变量与代码注册表是否一一对应、每条不变量是否有测试覆盖。

**为什么不再用"召回 100%"当门限**：门限假设"这个指标测到的就是患者安全"。但它测的是
一个自建小样本用例集上的比例——它既能漏掉用例集之外的形态，又会把"为了让闸门变绿而动尺子"
变成最省事的做法。一个永远红着的门限与一个可以调松的门限，最终都等于没有门限。
把指标降为**记录**之后，它反而能起到它真正能起的作用：趋势、回归、异常。

**为什么是这三层**，而不是一层做得更严：

- L1 只能尽量不漏。要求模型"多角度"（症状性质 / 组合共现 / 时间过程 / 严重度 / 高危人群 /
  情境诱因）并让每条信号带上 `likelihood` 与排除依据，是把它的判断**暴露出来**，
  而不是让它变成不会错；
- 暴露出来的不确定性必须有出口 ⇒ L2：没排除的危险信号**必须追问**（模型不问，服务端补一句
  确定性的追问）。这一层把"没识别出来"的风险转成"再问一句"的动作；
- 前两层都是模型，都可能失手 ⇒ L3 兜住"至少给对动作"。它只做三件能被事实锚定的事
  （无依据不给医学内容 / 不许声称未执行过的挂号动作 / 判了急症必须给可执行急救动作），
  **不做医学判断**——把需要判断的东西写成 `if` 语句，只会得到一个看起来安全、
  实际没人负责的假门。

**L3 里唯一"加内容"的那条**（判了急症必须给急救动作）方向与另外两条相反，这是刻意的：
安全性只能往上加。模型少写一句"打 120"不该让患者失去这句，所以判据只认**想去哪**
（120 / 急诊 / 救护车 / 立刻就医），不认"要注意"这类没有动作的措辞；判据还取**模型自己给出的
信号里更重的那一侧**——`critical` 严重度或 `likely` 的危险信号，即使 `urgency` 被写成了
`urgent`，也照样补动作并把这一轮升级为急症轮。

**治理做什么**：改安全资产（提示词 / 危险信号词表 / 症状词表 / 科室表 / 金标集）要更新
`data/governance/safety_assets.json` 的哈希与理由；运行期每次不变量触发都写一行审计
（**不记患者原话**）；评测报告带时间戳归档。这三件事让"改了什么、谁改的、为什么、
有没有效"都能查——而不是靠一句"我们会小心改"。

**接受的两个代价**：① 指标不再是自动门禁，需要人定期看档案（这是有意的：判断得由人负责）；
② `check_governance.py` 会因为资产改动而红，需要同步清单——那是变更控制的成本，不是缺陷。

**仍然保留的纪律**：**没测不等于测过**。闸门照样对"一条用例都没跑"与"有题目没拿到模型判断"
失败——否则删掉语料或掐断模型调用就成了让闸门变绿的手段。

## 25. 不确定性要有字段，而且要改变行为

**决定**：危险信号带 `likelihood`（`ruled_out` / `unlikely` / `possible` / `likely` /
`very_likely`），结论带 `confidence` 与 `information_gaps`。它们不只进留档，还改变行为：
`requires_emergency()` 为真的信号（`likely` / `very_likely`，或 `critical` 严重度）必须判成
`emergency`；`unresolved_signals()` 非空且不是急症 ⇒ 必须有追问；`confidence` 低于 0.6 ⇒
必须写清还缺什么信息。

**为什么不是"让模型谦虚一点"**：只要求模型说"我不确定"，得到的是一句没人能用的免责声明。
有用的形态是**可核对 + 有后果**：档位能比较（程序据此决定要不要追问）、排除必须给依据
（`ruled_out_by` 为空一律按未排除处理）、低置信必须说缺什么（否则患者无从判断这句话能不能信）。

**缺省值的方向也是刻意的**：`likelihood` 缺省是 `possible`（未排除）而不是 `ruled_out`，
`confidence` 缺省是 `None`（没给）而不是某个中间值。前者不让省略变成"已排除"，
后者不让"没量化"看起来像"量化过了"。

**自报置信度不作为概率使用**：它唯一的统计用途是校准报表（Brier + 可靠性分箱），
而且**只报告不上门限**——小样本上校准数字波动很大，拿它卡门禁等于用噪声判生死。
它到底可不可信，由报表本身回答。

## 26. 安全审计不记患者原话

**决定**：运行期审计（`data/index/safety_audit.jsonl`）只记不变量 id、处置动作、
一句固定的处置说明、`trace_id` 与时间戳，**不记患者原话、不记模型输出**。

**为什么**：审计的用途是"哪条底线在什么情况下被触发过"，这个用途不需要临床文本。
临床文本已经落在 `clinical` schema 里（有自己的访问控制与保留策略），在审计日志里再抄一份，
只是把同一份敏感数据多复制到一个访问控制更弱的地方。需要细节时按 `trace_id`
（= `encounter_id`）去临床库取——那条路径有它自己的权限。

配套两条：**没有触发就不建文件**（空文件会被读成"跑过、没问题"）；**写失败不影响这一轮
应答**（与落库同一条纪律），但要记 warning——静默失败等于审计是假的。

## 27. 评测跑产品路径，装配只有一处

**决定**：评测的判断臂改为跑**工具循环**（`pipeline.advance(原话)`），并且与 `/consult`
共用同一处装配——`clinical/runtime.py` 的 `build_clinical_assembly()`。单发
（`ClinicalReasoner`，不检索）保留为 `--arm reasoner` 对照臂。

**为什么**：评测的可信度取决于它测的是不是产品走的那条路。以前两边各写一遍装配
（工具注册、面板建造、预算账本、安全门），差异不会以报错的形式出现，而是以"评测在测一个
产品不会走的形状"的形式出现——分数看起来仍然合理，偏差却没人发现。装配收敛到一处之后，
**注入项**成了唯一的差异来源，而注入项是显式的：号源用替身、不落库、不写审计。
工具循环臂也因此能测到只有拿到证据才成立的约束（"检索不到就不给"）与
"判急症必须给动作"那条不变量——单发臂测不到它们。

**代价**：工具循环臂需要真实索引 + 密钥，会花钱（实测约 2.2 次模型调用/题、
￥0.0011/题量级），所以它不进 CI；单发臂留着当便宜对照。

## 28. 长期监听做"记录 + 比对"，不新增门限

**决定**：`scripts/monitor_clinic.py` 定期跑一轮评测，把结果追加成一行趋势记录，并与
最近几轮比对。`alert`（不变量被触发 / 这一轮没跑成 / 有题目没拿到判断）让退出码变 1；
`note`（召回下降、误报上升、分诊下降、单题花费上升、提示词或金标集变化）只打印，
默认不改退出码。

**为什么不加门限**：那会重新引入"用自建小样本的分数决定通过与否"的问题（见决策 24）。
但"只记录"也有代价——**没人看就等于没测**。监听解决的就是这个：它把"没变差"变成一件
可以自动检查的事，而不把模型波动变成红灯。

**为什么与历史区间比，而不是与人拍的阈值比**：阈值一旦写死，要么天天误报、要么被人改松。
"低于最近几轮的最低值 / 高于最高值"随样本自然收紧或放宽，不需要维护一个"合理误差"。
工具循环臂与单发臂**分开比**：数量级不同，混在一起比会得到假的回归。

**为什么复用评测脚本的 `main()`**：监听自己再写一遍评测，就会得到一份"和产品不一样"的趋势，
而那种偏差最难发现——与决策 27 是同一条理由。

配套一条运行期读数：`kubedocs_safety_invariant_fired_total{invariant,domain}`。
审计文件回答"发生了什么"，Prometheus 计数回答"最近是不是变多了"；告警规则写在计数上，
而不是让人去 tail 一个 JSONL 文件。
