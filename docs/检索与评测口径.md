# 检索与评测口径

这份文档回答一个问题：**"这个系统的检索质量数字，是怎么量出来的、能信到什么程度。"**
所有数字都在 README「实测数字」里，这里写的是**口径与边界**。

---

## 一、切块约定

| 标识 | 取值 | 用途 | 为什么不能用另一个 |
|---|---|---|---|
| `chunk_id` | `<doc_id>::<序号:04d>` | 主键、引用定位 | 它**位置相关**：换一次 `chunk_max_chars`，序号就全变，所以不能用于"内容是否变了" |
| `content_hash` | blake2b(块正文, digest_size=8) | 变更检测、**向量复用** | 它**内容相关**：同内容块哈希相同，因此能跨文档复用已算好的向量 |
| 文档级 `content_hash` | blake2b(文件原始字节) | 整篇跳过 | 读原始字节而非切块后文本：front matter 的变化（weight/description）不进正文，但往往意味着结构变了 |

块正文前会加一行上下文头 `[文档标题 › 标题面包屑]`。这不是装饰：实测它能
把**逐字重复块从 30.7% 压到 1.12%**（K8s API reference 有大量跨文档同形的模板小节）。
代价是每块长约 +30 字符。

## 二、检索两路各自的作用（不要混为一谈）

| | 强项 | 典型查询 | 弱项 |
|---|---|---|---|
| 全文路（FTS5 + `bm25()` + 列权重 1/3/1.5） | **精确词元** | `topologySpreadConstraints`、`--eviction-hard`、报错原文 | 改述就漏（问"一直重启"而文档写 "CrashLoopBackOff"） |
| 向量路（bge-small-en，余弦） | **改述/语义近邻** | "容器占用内存太多怎么办" | 标识符、版本号、参数名容易和近义词混淆 |

两路用 **RRF 融合**。为什么不做"归一化分数后加权"：BM25 分数**无上界且随语料长度漂移**，
余弦在 [0,1]，两者量纲不同；加权需要两个待调权重且**换语料就得重调**。RRF 只用名次：

    score(d) = Σ_r 1 / (k + rank_r(d))

免标定、跨语料稳定（Elasticsearch/OpenSearch 内置策略同源）。代价是丢掉分差信息，
`k` 需按语料规模调（本项目 60）。

**单路为空时不做稀释**：某一路返回空（例如向量模型不可用），只在**有结果的路上**求和；
否则会把另一路的结果整体压低。

### 降级必须是"有记录的降级"

向量路不可用时不抛异常、不改用静默的替代路径，而是：
退化为纯全文检索 + 把原因写进 `diagnostics.degraded`，`search --explain` / `--json` 可见。
**一个静默变成纯关键词的 RAG 系统，在评测里表现为"分数莫名掉了几个点"，排查成本极高。**

## 三、指标口径：为什么按**文档**判定相关性

块是**实现产物**：换一次切块参数，块 id 与边界全变，块级标注立刻作废。
文档级标注（"这个问题的答案在哪篇文档里"）在切块参数变化后依然有效，因此可以长期做回归基线。

四个指标一起看，因为单看任何一个都会被误导：

| 指标 | 回答的问题 | 单看它的盲区 |
|---|---|---|
| `hit@k` | top-k 里有没有命中 | 把正确答案从第 1 位挪到第 2 位，hit 完全不变 |
| `recall@k` | 多目标时命中了几个 | 单目标查询下等于 hit |
| `MRR@k` | 第一个正确结果排多前 | 忽略第 2 个及之后的目标 |
| `nDCG@k` | 整体排序质量（位置加权） | 不直观，且对相关性分级敏感（本项目用二值） |

结果按 **identifier / paraphrase / concept** 三类分别统计。分类型的意义在于：
它能直接暴露"某一路失效"——例如向量路挂掉时，paraphrase 类会明显掉而 identifier 类几乎不动。

## 四、评测器必须"能失败"：四道拒绝/失败条件

| # | 条件 | 触发时行为 | 防的是什么 |
|---|---|---|---|
| 1 | **标注集自检**：引用的文档必须在索引里，且 `must_contain` 关键词必须真的在该文档正文中 | **退出码 3，不产出任何分数** | 标注写了不存在的文档/记错的字段名 → 指标静默退化成噪声 |
| 2 | **引用完整性**：每条结果必须有可点击 URL，且该 URL 能由 `doc_id` **重新算出来** | 违规数 ≠ 0 即闸门失败 | URL 映射与存储内容漂移（引用变成死链而无人察觉） |
| 3 | **基线与标注集哈希绑定** | 哈希不同 → 拒绝比较 | 改了问题却拿旧基线比分数 |
| 4 | **语料漂移** | 索引块数变化 > 2% → 默认拒绝比较（`--allow-corpus-drift` 可放行并告警） | 跨语料比较分数 |
| 5 | **基线漂移容忍** | `hit@k` / `mrr@k` 相对基线下降 > 2pp → 退出码 2 | 检索质量回退 |

第 1 条不是纸上条款：写这 50 条标注时它当场抓出 **3 条写错的标注**
（我记成了 `targetCPUUtilizationPercentage`、`fieldSelector`、`emptyDir`，
而目标文档里实际是 `averageUtilization`、`field-selector`、`share a Volume`）。
没有这道检查，这 3 条会变成"看起来能跑、其实随机"的噪声。

## 五、诚实边界（能信到什么程度）

1. **50 条查询的统计功效有限**。二项比例在 p≈0.9、n=50 时标准误约 4.2pp，
   95% 置信区间约 ±8pp。2pp 的闸门容差 **≈ 1 条查询**。所以：
   **闸门是"冒烟探测器"，不是显著性检验**——它用于抓明显回退（例如某一路直接失效、
   索引漏建），不足以支撑"新版比旧版好 1.5%"这类结论。要做后者需要扩标注集（200+ 条）。
2. **单路消融 ≠ 因果归因**。它只能说明"在这个标注集与这套参数下，两路融合优于单路"，
   不能说明各路的贡献可以线性分解。
3. **哈希向量模式（`--provider hashing`）的分数不代表检索质量**。它只做字面重合，
   存在的意义是让管道可离线自测、让 CI 不下载模型。**任何质量结论都必须用真实模型跑。**
4. **索引小的时候 hit@k 会虚高**：库里只有两三篇文档时，top-5 几乎必中。
   所以小规模测试里的高分没有意义，评测必须在全量语料上跑。
5. **精排（cross-encoder）默认关闭且尚未用真实模型实测**。代码与降级路径有单测覆盖，
   但"它到底提升多少"没有数据 —— 在没有数据之前不写进结论。
6. **暴力向量检索**在 2 万块量级是毫秒级；超过约 100 万块需要换 ANN（HNSW/IVF）。
7. **超长块会被嵌入模型静默截断**（bge-small max_seq=512）。摄取会明确计数并打印
   （全量语料里约 36 块），但**块尾部内容在向量路上是检索不到的**——
   它仍可通过全文路命中。这是一个已知局限，不是 bug。

## 六、复现一次评测需要什么

```bash
python scripts/check_gold.py                      # 1) 标注集预检（对原始语料，秒级）
python -m kubedocs.cli --hf-offline eval --gate    # 2) 评分 + 单路消融 + 卡闸门
```

评测**不需要** LLM 密钥、不需要网络（模型已缓存时加 `--hf-offline`）、不需要容器。
这正是把"业务逻辑"与"可复现部署"拆开的价值（见 [ADR-0002](adr/0002-先跑通业务逻辑.md)）。
