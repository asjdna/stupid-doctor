## 一、背景

ADR-0004 决定了前三个后端（`sqlite` / `sqlite-vec` / `pgvector`），并留下一条边界：

- `sqlite-vec` 的 `vec0` 是 **C 实现的穷举扫描**，不是 ANN。它的优点是"向量与块行同事务"，
  代价是延迟随块数线性增长（实测比 numpy 暴力还慢约 11 倍）；
- 真正需要 ANN 时，当时的答案是 **pgvector HNSW**——但那要一个 Postgres 实例。

于是出现一个空缺：**想要 ANN，又不想起外部服务**。Milvus Lite 正好补这个位：
它是 milvus 的嵌入式形态，索引跑在本地**文件**里，不需要容器、不需要网络。

## 二、决策

**新增第四个 `Store` 实现 `milvus`：SQLite（FTS5 全文，复用既有实现） +
Milvus Lite 本地文件（HNSW 向量）。**

它是本项目**唯一真正提供 ANN 的嵌入式后端**——这句是本后端存在的全部理由。

## 三、四个后端的对照

| | `sqlite` | `sqlite-vec`（默认） | `milvus` | `pgvector` |
|---|---|---|---|---|
| 全文 | SQLite **FTS5** + `bm25()` | 同左（**同一份索引、同一段代码**） | 同左 | `tsvector` + GIN + pg_search BM25 |
| 向量 | numpy 暴力内积 | `vec0` 虚表（穷举扫描，非 ANN） | **HNSW**（milvus-lite 内置 knowhere） | HNSW（服务端） |
| 向量存放 | `.npy` 侧车矩阵 | 与块行**同一事务** | **另一个数据目录**，与 SQLite 不同事务 | 与块行同一行 |
| 需要外部服务 | 否 | 否 | 否（本地文件模式） | 是（Postgres） |
| 多进程 | 单写多读（WAL） | 单写多读（WAL） | **独占**（同一目录只允许一个进程） | 多实例并发 |

**为什么继承 `SqliteStore`**：与 `SqliteVecStore` 同一个理由——两者之间**唯一的变量是向量路**。
全文路共用 FTS5 外内容表、同一段 `keyword_search`、同一组 BM25 列权重，因此
`sqlite` / `sqlite-vec` / `milvus` 三者的全文结果**逐字节相同**；指标若有变化，
只可能来自向量路。这对"换后端到底改了什么"的归因是决定性的。

## 四、唯一真正的代价：向量与块行**不再同事务**（以及怎么处理）

`sqlite-vec` 把向量写进同一个 SQLite 事务，所以不存在中间态。Milvus Lite 是**另一个
数据目录、另一个引擎**，没有跨引擎事务可用。本实现的处理是**显式排序 + 显式检测**：

1. `upsert_docs` 里向量写 Milvus 发生在 SQLite **提交之前**（`_index_chunk_vectors`
   钩子在事务里）。因此 **Milvus 写失败 → 抛错 → SQLite 事务回滚**，
   不会留下"块写了、向量没写"的中间态。这是刻意选的顺序。
2. 反过来（Milvus 已写、SQLite 提交失败）会留下**孤儿向量**。这一侧无法用事务消掉，
   所以改为**检测**：`_refresh_vec_ready()` 在每次打开与每次 `finalize()` 核对
   "块表行数 vs 向量行数"，不一致就**拒绝向量检索**（抛 `StoreError` 并给修复命令）；
   `verify_vec()` 另做一次**主键集合**级核对。
3. 已知无法检测的残留窗口：整批 Milvus 写成功、SQLite 提交失败、且两次写入的
   `chunk_id` 完全相同（改写同一篇文档）——行数与主键集合都相同，只有向量内容是旧的。
   处理方式是 `scripts/migrate_to_milvus.py` 重灌或 `ingest --rebuild`。

**把这条写在这里，是因为"没法用事务保证"和"我们假装它没问题"是两种不同的东西。**

## 五、实测（2026-10-12，本机 Windows / CPU）

### 5.1 数据路径与一致性

用 `hashing` 占位向量建了 3000 块 × 64 维的 milvus 索引（`scripts`/一次性脚本，非生产数据）：

```
milvus 数据路径: <index_dir>/<domain>/milvus.db
是目录吗: True   目录内容: ['.database-staging', 'LOCK', 'collections', 'databases']
verify_vec: ok   verify_fts: ok
```

⇒ 与实现里的两条硬约束一致：**`<...>.db` 在 milvus-lite 眼里是目录**（备份/清理要按目录处理），
里面有 `LOCK` 文件——它就是"同一目录只允许一个进程"的载体。

### 5.2 HNSW 召回 vs 精确检索（同一查询集，top-10，3000 块 × 64 维）

| `ef`（查询期） | 与精确内积**逐位相同** | 平均集合重合 | 平均耗时 |
|---|---|---|---|
| 16 | **50/50** | 1.0000 | 682.8 ms/查询 |
| 64 | **50/50** | 1.0000 | 698.6 ms/查询 |
| 128 | **50/50** | 1.0000 | 679.9 ms/查询 |
| 256 | **50/50** | 1.0000 | 728.6 ms/查询 |

**两条结论，一条与直觉相反：**

1. **在 3000 块这个量级，HNSW 的"近似"根本没体现出来**——四个 `ef` 取值都与精确检索
   **逐位相同**。也就是说这里测到的召回优势是 0，`ef` 也就没有可调的空间。
   （这与 ADR-0004 第六之二节的结论同向：**"换成 HNSW 就能提升"在本量级上不成立**。
   要看出 HNSW 的取舍，得跑到百万块量级，本项目没有那个规模的数据。）
2. **它的单查询延迟远高于 `sqlite-vec`**：这里是 **~0.7 秒/查询**，而本项目在其他
   ADR 里记录的同规模 `sqlite-vec` KNN 是 **~12 ms**（调过页缓存之后）。
   差距来自"跨引擎调用的固定开销"（milvus-lite 本地模式每次查询都要过客户端层），
   在 3000 块这种小规模上它完全盖过了向量计算本身。

⇒ 所以本后端的定位要写清楚：**它提供的不是"更快"，而是"一个真正 ANN 的嵌入式选项"**。
在本项目的语料规模（1.9 万块）上，**默认后端 `sqlite-vec` 依然是更快的选择**；
`milvus` 的价值在于"当块数涨到穷举扫描真的扛不住时，有一个不需要外部服务的退路"。

> 口径说明：上表是**本机、本规模、hashing 向量**下的一次测量，n=50 条查询。
> 它足以说明"ef 在这个规模上没有可测收益"与"固定开销很大"这两件事，
> 但**不足以**给出任何关于生产规模下 HNSW 延迟/召回的结论——那需要 10⁵~10⁶ 块的数据。

### 5.3 独占锁

实现与测试都建立在"同一数据目录同一时刻只允许一个进程打开"这条性质上
（第二个进程报 `DataDirLockedError: another process holds the lock`），
`tests/unit/test_milvus_store.py` 用**跨进程**实测把它钉住。
本轮**未重跑**那一次跨进程实测（它需要子进程，与本轮的其他长任务争 CPU），
所以这里只标注结论**来自既有测试**，不冒充本轮新测。

**运维含义**：API 服务开着的时候，CLI 的 `ingest` / `eval` **打不开同一份 milvus 索引**。
这比 SQLite 的 WAL（单写多读）严格，是本后端最实在的运维代价。

### 5.4 参数与元信息

- `M = 16`、`efConstruction = 200`（**建索引参数，改了必须重建**）；查询期 `ef` 默认 128。
  5.2 表明在当前规模上 `ef` 没有可测收益，但它是查询期可调项，**不需要重建索引**。
- 度量默认 **COSINE**，与 `sqlite-vec` 的 `distance_metric=cosine`、pgvector 的
  `vector_cosine_ops` 一致；本项目向量已归一化，此时余弦序与内积序严格相同。
- Milvus Lite **不回传**索引参数（`describe_index` 只有 index_type/metric_type/field_name），
  所以本实现把 `M` / `efConstruction` / 度量写进 SQLite 元信息（`milvus_hnsw_*`），
  配置与索引不一致时**报错**，而不是静默沿用一个参数不同的旧索引。

## 六、不可用就报错，绝不回退

未安装 `pymilvus`/`milvus-lite`、数据目录打不开（最常见的是被另一个进程独占）、
初始化失败——一律抛 `StoreError` 并给出可执行的修复提示。**不会**退回 numpy 暴力扫描：
本项目明确禁止静默降级——"我明明配了 milvus，为什么排序和 sqlite 一模一样"
必须是一个能被发现的配置问题。

依赖是**可选**的：`pymilvus` / `milvus-lite` **没有写进 `pyproject.toml`**，
CI 也就不装，于是 `tests/unit/test_milvus_store.py` 与 `test_store_contract.py` 的
milvus 参数在 CI 里会**整族 skip**（`-rs` 会打印原因）。本机装了它们，所以本轮
这些用例是**真跑**的。
