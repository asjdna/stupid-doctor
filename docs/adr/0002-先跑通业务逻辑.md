# ADR-0002：先让业务逻辑在本机跑通——SQLite+FTS5+numpy 作为默认存储

- 状态：已接受
- 日期：2026-09-24
- 相关：ADR-0001（技术选型）

## 背景

ADR-0001 把 Postgres+pgvector 定为存储方案，并且整个项目按"一条 `docker compose up`
起全栈"来组织。实际推进时这条路被卡住了，**卡点不在设计而在环境**：

| 事实 | 后果 |
|---|---|
| Docker Hub（`registry-1.docker.io` / `auth.docker.io`）在本网络被拒 | 拉不到任何基础镜像 |
| 镜像站可拉（`docker.m.daocloud.io` 实测 2.9s 拉下 hello-world） | 但 Docker Desktop 会**覆盖** `~/.docker/daemon.json`，镜像加速配置不生效 |
| 当前 shell 无管理员权限 | 起不了需要提权的 Docker Engine 方案 |
| huggingface.co 不可达（走 hf-mirror 才行） | 已解决，但说明本环境网络是白名单式的 |

于是出现了一个**优先级错配**：为了让容器跑起来而反复折腾环境，而真正要交付的
业务逻辑（切块 → 嵌入 → 混合检索 → 引用 → 评测）一行都还没跑通。

## 决定

**把"业务逻辑跑通"与"一键可复现部署"拆成两个目标，先完成前者。**

默认存储改为 **SQLite（FTS5 全文）+ numpy 向量矩阵**，检索与生成代码只依赖一个
窄接口 `Store`，因此这次改动**没有触及** `retrieve/`、`ingest/`、`eval` 的任何一行逻辑。

| 关注点 | pgvector 方案 | 本地默认方案 |
|---|---|---|
| 全文检索 | Postgres `english` 配置 | SQLite **FTS5**（`porter unicode61` 分词 + 内置 `bm25()` 排序） |
| 向量检索 | pgvector HNSW/IVF | numpy 暴力内积（18861×384 ≈ 29 MB，毫秒级） |
| 部署依赖 | 一个 Postgres 进程 + 一个扩展 | **无**（标准库 + numpy） |
| 事务一致 | 是 | 是（单文件 + WAL） |

## 为什么这不是"降级实现"

1. **接口相同**：`Store` 协议只暴露 8 个操作，pgvector 版实现同一协议即可切换，
   调用方零改动。这正是当初把接口写窄的回报。
2. **能力没有缺失**：FTS5 自带真正的 BM25 排序函数（不是 `LIKE` 打分），
   还支持列权重，能把标题命中的块往上提——与 pgvector 方案里的做法等价。
3. **可验证**：本方案下已经跑出真实的端到端数字（见 README「实测数字」），
   而不是停留在"文件已写、未实测"。

## 代价与边界（写清楚，避免日后误判）

| 边界 | 具体限制 | 触发后该做什么 |
|---|---|---|
| 单写者 | SQLite 并发写有限，只适合单进程摄取 | 线上多实例写 → 换 pgvector 版 |
| 无 ANN | 暴力内积在 10 万块量级仍是毫秒级 | 超过 ~100 万块 → HNSW/IVF |
| 向量常驻内存 | 当前 384 维 × 2 万块 ≈ 29 MB | 维度或规模上去后需分片/落盘索引 |
| 无 RLS/多租户 | 单文件单租户 | 多租户 → pgvector 版 + 表级 RLS |

## 对 ADR-0001 的修正

- 「存储」一行的决定从"Postgres+pgvector"改为"**默认本地 SQLite+FTS5+numpy；
  pgvector 作为同协议的生产实现**"。选型判断本身没变（依然是一库承担全文+向量），
  变的是**先做哪一个**。
- ADR-0001 第三节"留待验证的假设"第 1 条（compose 全栈未实测）保持未完成状态，
  按"没跑过就不写已完成"的纪律继续标注为未验证。
- 新增一条已实测的假设结论：**本地 BGE-small-en 在本机 CPU 上的嵌入吞吐约 9.4 块/秒**
  （i7-13700H，14 核，纯 CPU torch 2.11）。这个数字决定了一次全量摄取的时长，
  也说明**嵌入是整条链路的成本瓶颈**，后续应优先考虑量化/ONNX 或改为增量编码。
