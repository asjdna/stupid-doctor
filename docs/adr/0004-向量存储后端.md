# ADR-0004：向量存储后端——默认嵌入式 ANN 位（sqlite-vec）+ 生产 pgvector

- 状态：已接受（三个后端都已在本机真跑；**pgvector 的混合检索质量低于冻结基线**，
  根因已定位为「Postgres 核心没有 BM25」，**与 HNSW 无关**；待决策项见第九节）
- 日期：2026-09-26（2026-10-09 补 pgvector 实测、HNSW 召回度量，并新增第九节）
- 相关：ADR-0001（技术选型：存储定为 Postgres+pgvector）、ADR-0002（先跑通业务逻辑：
  默认退回 SQLite+FTS5+numpy）、ADR-0003（双域 Agent 平台）
- 影响面：`src/kubedocs/store/`（新增两个实现 + 后端选择）、`config.py`（`KUBEDOCS_STORE`
  与 HNSW/页缓存参数）、`scripts/`（迁移与基准脚本）。`ingest` / `retrieve` / `generate` /
  `api` 的**检索与生成逻辑一行未改**（只把类型标注从 `SqliteStore` 换成 `Store` 协议）。

## 一、背景：ADR-0002 留下的两条边界到期了

ADR-0002 把默认存储定为"SQLite(FTS5) + numpy 暴力内积"，并写明三条代价：

| 边界 | ADR-0002 的原文 | 现在的状态 |
|---|---|---|
| 单写者 | 「线上多实例写 → 换 pgvector 版」 | 生产实现已补齐（本 ADR） |
| 无 ANN | 「超过 ~100 万块 → HNSW/IVF」 | 本地用 sqlite-vec 位替换，**但它不是 ANN**（见第六节） |
| 向量常驻内存 + 删除要重建矩阵 | 未写进 ADR-0002，是实现的隐含代价 | 新默认实现消掉了这一条 |

同时 ADR-0001 第三节「留待验证的假设」第 2 条（Postgres 全文检索对 K8s 文档的召回质量）
一直没有数据。本 ADR 给出**同一份标注集、同一批查询、同一批向量**下的两路对照。

> **2026-10-09 补记（先说结论）**：pgvector 一路当时因环境（Docker 未起来）只能标注为
> "未验证"，现在已在本机 `pgvector/pgvector:pg16` 容器上真跑（表在 `k8s_docs` schema 下，
> 18861 块 / 1720 文档，与本地索引同一份数据）。结论是**否定**的——ADR-0001 那个假设
> **不成立**：Postgres 核心的全文检索把 hybrid hit@10 从 0.84 拉到 0.74、recall 从 0.76
> 拉到 0.68，而向量路（HNSW）几乎无影响。数字与归因见 5.3，待决策项见第九节。

## 二、决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **新增 `SqliteVecStore`（SQLite + sqlite-vec），并把它设为本地/CI 默认** | 向量与块行同事务、可增删、不常驻内存、不需要 `.npy` 侧车文件 |
| D2 | **新增 `PgVectorStore`（Postgres + pgvector HNSW）作为生产实现** | 多实例写、一库承担全文+向量、schema 级多租户 |
| D3 | **旧实现 `SqliteStore` 保留**，不被删除 | 它是唯一"零扩展、纯 numpy"的实现，可回退；也是性能对照的基线（删掉这列数字就再也复现不了） |
| D4 | **后端由 `KUBEDOCS_STORE` 选择，默认 `sqlite-vec`；非法值直接报错，绝不静默回退** | 静默回退会让"我明明切到 pgvector 了，为什么数据还是旧的"变成一个没有日志的谜 |
| D5 | **`Store` 协议补齐运维操作**（`rebuild_from_scratch` / `verify_fts` / `meta_dump` / `doc_summary` / `close`），调用方类型统一到 `Store` | 协议不写全，pgvector 版就得靠 `cast`/`getattr` 绕过类型检查，等于把"可替换"作废 |

## 三、三个实现的定位与要点

| | `sqlite-vec`（默认） | `sqlite`（旧） | `pgvector`（生产） |
|---|---|---|---|
| 全文 | SQLite **FTS5** + `bm25()`，列权重 `(body 1.0, title 3.0, breadcrumb 1.5)` | 同左（**同一份索引、同一段代码**） | `tsvector`（生成列）+ GIN + `ts_rank` |
| 向量 | `vec0` 虚表，**主键 = `chunk_id`**，`distance_metric=cosine` | numpy 矩阵内积（`argpartition`） | `vector(384)` + **HNSW**（`vector_cosine_ops`） |
| 向量存放 | DB 内虚表，与块行**同事务** | `.npy` 侧车文件 + `finalize()` 重建矩阵 | 与块行同一行（`NOT NULL`） |
| 删除一篇文档 | 按 `chunk_id` 删除行 | 重建整份矩阵（18861×384 ≈ 29MB 重写） | `ON DELETE CASCADE` |
| 内存 | 不常驻 | 全量向量常驻（29MB） | 不常驻（服务端） |

### 为什么 sqlite-vec 用 `chunk_id` 当向量表主键

旧实现必须绕道 `chunks.rowid`，于是要处理"SQLite 会回收最大 rowid"这个坑
（`finalize()` 里重建矩阵并回写 `vector_row` 就是为了它）。直接用 `chunk_id`
作 `vec0` 的主键后，这个坑**不存在**：覆盖与删除都按主键定位，
不存在"行号错位"这种可能。

### pgvector 的 HNSW 参数（`m=16` / `ef_construction=64` / `ef_search=200`）

- `m=16`：每个节点的出边数，pgvector 默认值。1.9 万块规模下 `m=8` 会明显掉召回，
  32 以上收益递减而索引体积与建图时间线性上升。**只能重建索引才能改**。
- `ef_construction=64`：建图候选队列，默认值。与 `m` 一起决定图质量；
  本规模下建索引只需数秒，调到 200 的收益要在更大规模上才看得到。
- `ef_search=200`（pgvector 默认 40，**查询期**参数，不需要重建索引）：本仓库原先取 100，
  2026-10-09 起提到 200，依据是同轮实测（18861 块真实索引，50 条金标 ×3 轮，
  原始数据 `data/eval/store_bench/latency_pgvector_ef{100,200,400}.json`）：

  | `ef_search` | 向量路 top-10 与 numpy 精确检索逐位相同 | 平均集合重合 | dense p50 |
  |---|---|---|---|
  | 100 | 36/50 | 0.9420 | 4.29 ms |
  | **200（现默认）** | **43/50** | **0.9800** | **5.79 ms** |
  | 400 | 44/50 | 0.9840 | 7.24 ms |

  100 → 200 多找回 7 条查询的完全一致、代价 +1.5ms；200 → 400 只多 1 条却再贵 1.45ms，
  **收益明显递减**，所以停在 200。三者都通过 `KUBEDOCS_PG_HNSW_*` 可调。
  ⚠️ 这个旋钮**治不了**混合检索的质量落差：ef=100/200/400 下 hybrid 的
  hit/recall/MRR/nDCG 完全相同（0.74 / 0.68 / 0.5157 / 0.5369），因为落差出在全文路。
- 距离用余弦（`<=>` + `vector_cosine_ops`）：与另外两个实现语义一致；
  向量已归一化时余弦序与内积序严格相同。

### 全文的**真实差异**（不粉饰，尤其中文）

1. **排序函数不同源**：FTS5 是真 BM25（含 IDF 与文档长度归一化）；
   Postgres 核心**没有 BM25**，用的是 `ts_rank`（TF 加权，无 IDF、无长度归一化）。
   列权重通过 `setweight` + `ts_rank(weights,...)` 对齐到同名权重，
   但**相同命中集合下的排序仍可能不同**——常见词与稀有词的相对权重不同源。
   要 BM25 得装扩展（ParadeDB/pg_search），本次不引入。
   **实测的影响（2026-10-09 修正）**：原先这里写的是"指标全部未变，说明差异未外显到
   指标层"——**那句话是错的**（它的依据是"pgvector 跑都没跑过"）。真跑出来差异是显著的：
   hybrid hit@10 0.84 → 0.74、recall 0.76 → 0.68、bm25-only hit 0.70 → 0.54，
   而 dense-only 一位不变（0.78）。全文路 top-10 与 FTS5 的**集合相同数为 0/50**，
   平均集合重合仅 0.3140（其中 9/50 条查询完全不重合）。见 5.3。
2. **词干与停用词**：`english` 配置 = Snowball 词干 + 英文停用词表；
   FTS5 的 `porter` 只做词干、**不删停用词**。查询侧我们已自行去停用词，
   但索引侧 Postgres 会把纯停用词的行索引成空。
3. **分词器不同**：Postgres 默认解析器 vs FTS5 `unicode61`。
   对 `kube-apiserver`、`--eviction-hard`、`v1.29` 这类标识符两者都按非字母数字切，
   但边界情况（下划线、点号与数字组合）不完全一致。
4. **中文（必须写明）**：**Postgres 侧没有 jieba**。本实现的做法是把
   **应用层的归一化文本** `body_normalized`（中文域即 jieba 预分词结果）写进库，
   再 `to_tsvector('english', body_normalized)` 建索引。所以：
   - 中文**能**检索，但能力来自**应用层归一化器**，不来自 Postgres；
     与 SQLite 侧用的是同一个 `Normalizer`，因此两侧的中文切分一致；
   - `english` 配置会对中文词元跑 Snowball 词干（对 CJK 是空操作），无害；
   - 若把中文语料配 `normalizer=identity`，Postgres 与 FTS5 **一样**会把整句
     当成一个词元——这不是 Postgres 独有的缺陷；
   - 想在库内做中文分词需要 zhparser/pg_jieba 扩展，本次**未引入、未验证**。
5. **结构性优势**：`tsv` 是 `GENERATED ... STORED` 生成列，**不可能与正文漂移**；
   FTS5 是外内容表，删除顺序写错就会永久不一致（`sqlite_store.py` 文档第 1 条）。
6. 并列分数的次序：Postgres 侧显式按 `chunk_id` 定序（确定性）；
   FTS5 的并列次序由内部实现决定，不应依赖。

## 四、后端选择

```
KUBEDOCS_STORE=sqlite-vec   # 默认：本地/CI，零外部进程、零镜像、零网络
KUBEDOCS_STORE=sqlite       # 旧实现：回退与性能对照
KUBEDOCS_STORE=pgvector     # 生产：Postgres + pgvector（需 KUBEDOCS_DATABASE_URL 可达）
```

- 默认值写在 `Settings.store` 的类型化字段上（不是散落的 `os.getenv`），
  非法取值在**启动时**被 pydantic 的字面量校验挡住；工厂里再兜一层
  （防止有人绕过 `Settings` 直接调 `from_settings`）。
- 工厂延迟导入各实现：只想用 `sqlite` 时，不该因为缺 sqlite-vec 扩展
  或没装 psycopg 而起不来。
- **没有回退链**：`sqlite-vec` 扩展加载失败就报错，不会"悄悄换成 numpy 暴力扫描"。

## 五、实测（同一份 18861 块 / 384 维真实索引，同一台机器）

### 5.1 存储层延迟（`scripts/bench_store_latency.py`，top_k=10，各 150 次采样）

**2026-10-09 同一轮、三个后端一起测**（`--backends all --repeats 3`；原始输出
`data/eval/store_bench/bench_all_ef200_raw.txt`，结构化结果 `latency_all_ef200.json`）：

| 后端 | dense p50 | dense p95 | keyword p50 | keyword p95 |
|---|---|---|---|---|
| `sqlite`（numpy 暴力内积） | **2.01 ms** | **2.54 ms** | 14.01 ms | 26.05 ms |
| `sqlite-vec`（vec0，调大页缓存后） | 22.36 ms | 26.54 ms | **13.30 ms** | **25.91 ms** |
| `pgvector`（HNSW，`ef_search=200`） | 5.57 ms | 7.59 ms | 47.86 ms | 92.65 ms |

- 跨后端 **top-10 一致性**：`sqlite-vec` 向量路 150/150 逐位相同、全文路 150/150；
  `pgvector` 向量路 **129/150 逐位相同（平均集合重合 0.9800）**、全文路 **0/150（0.3140）**。
  后者不是"向量坏了"，而是排序函数不同源（5.3 与第九节）。
- 样本为 50 条金标查询 × 3 轮 = 150；查询编码（bge，约 30~45 ms/条）**不计入**延迟。
- 该脚本刻意**分别**测两路：交错测时向量路 p50 会从 13ms 涨到 21ms
  （FTS 与向量表的页访问互相挤占页缓存），那个数字既不是向量延迟也不是全文延迟。
- 2026-10-08 那一轮的两个 SQLite 数字（`sqlite` 1.83 / 2.17、`sqlite-vec` 20.31 / 21.41，
  原始数据 `latency.json`）与上表**同向**（`sqlite-vec` 慢约 11 倍），差值属机器状态噪声。

### 5.2 换后端**没有**改变检索指标（**仅限两个 SQLite 后端之间**；`cli eval`，50 条金标，top_k=10）

| 指标（hybrid） | 改前 `sqlite`（冻结基线） | 改后 `sqlite-vec` | 差异 |
|---|---|---|---|
| hit@10 | 0.8400 | 0.8400 | **0** |
| recall@10 | 0.7600 | 0.7600 | **0** |
| MRR@10 | 0.5205 | 0.5205 | **0** |
| nDCG@10 | 0.5464 | 0.5464 | **0** |

单路消融也逐位相同：`bm25-only` hit 0.70 / MRR 0.3787；`dense-only` hit 0.78 / MRR 0.4253；
未命中条数同为 8 / 15 / 11；引用完整性违规 0。
`cli eval --gate` 在两个后端上都**通过**（与 `data/eval/retrieval_baseline.json` 的冻结基线比较）。
2026-10-09 复核：在冻结基线的同一份数据上重跑 `sqlite-vec`，四项指标**逐位复现**基线
（含 MRR 0.5205 / nDCG 0.5464）——原始输出 `data/eval/store_bench/attrib_pgvector_raw.txt`
里的 `sqlite-vec（基线口径）` 一行，结构化结果见 `eval_pgvector_attrib.json`。

**为什么完全没变**：两个 SQLite 后端共用同一份 FTS5 索引与同一段 `keyword_search`
代码（全文路逐字节相同）；向量路在向量已归一化时"内积序 == 余弦序"，
且 vec0 是**穷举**扫描（不是近似），所以 top-k 也完全相同。
换句话说：这一路替换是**存储形态**的改变，不是**检索语义**的改变——这正是它可验证的原因。

> ⚠️ **这一节的标题以前没有"仅限两个 SQLite 后端之间"这个限定**，于是它被读成了
> "换任何后端都不改指标"，而 pgvector 一路当时根本没跑过。5.3 就是那句话的实测反驳。
> 这条纪律本身没错（`store/base.py` 的协议文档也这么要求），错的是**在没跑过的时候就下结论**。

### 5.3 pgvector：从"未验证"到实测——指标**确实**退化，根因在全文路

#### 5.3.1 先说历史：这条路曾经**从来没有被执行过**

在拿到下面的数字之前，`PgVectorStore` 的代码、DDL、脚本、测试都已写好，但**一次都没跑通**。
第一次真跑（本机起 `pgvector/pgvector:pg16`、`scripts/load_pgvector.py` 灌 18861 块）连续
暴露出 5 个缺陷，它们的共同点是**只有"代码从未被执行过"时才可能存在**：

| # | 缺陷 | 不跑就看不出来的原因 | 现状 |
|---|---|---|---|
| 1 | 池在 schema 初始化**之前** open → `register_vector` 要 `vector` 类型、而建扩展只能靠池的连接 → **自锁死**（连接池 10s 后 `PoolTimeout`，报 `vector type not found in the database`，而 `CREATE EXTENSION` 那句压根没执行到） | 静态看"先建池再建表"完全合理 | 已改为**直连建 schema → 再开池**（`PgVectorStore.__init__` 里的顺序注释） |
| 2 | `configure` 回调末尾没有 `commit()`，连接被判 `status INTRANS by configure function: discarded`，池永远填不满 | 只有真取连接才会暴露 | 已在 `_configure_connection` 结尾提交 |
| 3 | `Connection.executemany` **不存在**（只有 `Cursor` 上有），元信息初始化必抛 `AttributeError` | 抄的是 sqlite3 的心智模型 | 已改为显式 `with conn.cursor() as cur` |
| 4 | `pgvector` 的 `Vector` **不是 `ndarray` 子类**，`np.asarray()` 会报 `float() argument must be ... not 'Vector'` | 类型标注上它看起来像数组 | 已有 `_as_vector()` 走 `to_numpy()` 兼容两条路 |
| 5 | `ts_rank` 的权重**必须落在 [0, 1]**，照抄 `bm25(chunks_fts, 1.0, 3.0, 1.5)` 会直接抛 `weight out of range`，全文路一次都调不通 | SQL 文本本身看不出这条约束 | 已改成同比例、最大值为 1 的 `_TS_RANK_WEIGHTS` |

换句话说：**"未验证"在那时是诚实的描述，而不是一句客套**——代码在磁盘上存在，与它能跑
之间隔着上面这 5 条。这也是本节所有数字都带命令与落盘文件的原因。

#### 5.3.3 归因：把两路**分别**换回来

光看 5.3.2 还只能说明"某一处坏了"。把全文路与向量路**拆开替换**（同一个 `HybridRetriever`、
同一份 RRF 融合、同一份金标；脚本为一次性归因脚本，原始输出
`data/eval/store_bench/attrib_pgvector_raw.txt`，结构化结果 `eval_pgvector_attrib.json`）：

| 变体（全文路 / 向量路） | hybrid hit@10 | recall | MRR | nDCG |
|---|---|---|---|---|
| FTS5 + numpy 精确（= 基线口径） | 0.8400 | 0.7600 | 0.5205 | 0.5464 |
| FTS5 + **pgvector 精确** | **0.8400** | **0.7600** | **0.5205** | **0.5464** |
| FTS5 + pgvector HNSW(ef=100) | 0.8400 | 0.7600 | 0.5199 | 0.5458 |
| **`ts_rank`** + pgvector 精确 | 0.7400 | 0.6800 | 0.5140 | 0.5355 |
| `ts_rank` + pgvector HNSW(ef=100/200/400) | 0.7400 | 0.6800 | 0.5157 | 0.5369 |

结论三条，都有上面这张表逐格支撑：

1. **全文路换回 FTS5 BM25（配精确向量）后四项指标逐位回到冻结基线（Δ = 0）** ——
   落差**全部**来自全文路。这条同时也证明我的测量口径与冻结基线可比（同标注集哈希
   `3eee2503682df8ca`、同 18861 块、同嵌入模型）。
2. **与 HNSW 无关**：把向量路换成 `dense_search_exact()`（关掉索引扫描的精确检索）后，
   hit/recall 仍是 0.74/0.68。HNSW 的代价小到只在 MRR/nDCG 上体现：FTS5 + HNSW 时
   0.5199/0.5458，比基线的 0.5205/0.5464 低 0.0006。
3. **`ef_search` 不是旋钮**：100/200/400 三档的 hybrid 四项指标**一模一样**（0.7400/0.6800/
   0.5157/0.5369）。想靠调 `ef_search` 把 0.74 拉回 0.84 是徒劳的——它只影响向量路，
   而向量路本来就没退化。

#### 5.3.4 全文路的差异有多大：top-10 集合 0/50 相同

- **集合相同数 0/50**（名次逐位相同同样 0/50），**平均集合重合 0.3140**，
  其中 9/50 条查询的 top-10 与 FTS5 **完全不重合**（`eval_pgvector_attrib.json` 的
  `keyword_overlap`）。这不是"排序略微不同"，是**召回面本身换了**：
  `ts_rank` 没有 IDF，于是一个出现在几乎所有文档里的词与一个稀有标识符在排序里
  权重相近，top-10 被常见词挤满。
- 计量口径：`bench_store_latency.py` 的 `_agreement()` 同时报"名次逐个相同"与"集合相同"
  两个档位；把两者混为一谈会把"排序变了"误读成"召回坏了"（或反过来）。

#### 5.3.5 pgvector 全文路为什么慢：GIN 用不上，退化成 `Seq Scan`

同一批 50 条金标查询，用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 抓真实执行计划
（`eval_pgvector_attrib.json` 的 `plans`）：

| 计划类型 | 条数 | 执行时间 p50 | 执行时间 max |
|---|---|---|---|
| `Seq Scan`（GIN 没被用上） | **37/50** | 54.5 ms | 69.4 ms |
| `Bitmap Index Scan`（GIN 生效） | 13/50 | **1.0 ms** | 17.7 ms |

两个可复核的样本（同一份数据、同一个索引）：

- `kubectl drain --ignore-daemonsets --delete-emptydir-data`
  → tsquery `'kubectl' | 'drain' | 'ignore' | 'daemonsets' | 'delete' | 'emptydir' | 'data'`，
  计划 `Limit → Sort → Seq Scan`，**54.42 ms**；
- `topologySpreadConstraints maxSkew`
  → tsquery `'topologyspreadconstraints' | 'maxskew'`，
  计划 `Limit → Sort ← Bitmap Heap Scan ← Bitmap Index Scan`，**0.39 ms**。

**原因不是"Postgres 慢"，是查询形状**：本实现把多词查询拼成 `OR` 的 `to_tsquery`，
命中面一旦铺开到大部分行，GIN 位图反倒不如顺扫（规划器据此选 `Seq Scan` 是正确的）。
稀有标识符查询（本语料里 13/50 条）走 GIN 只要 **0.39 ~ 17.7 ms**（p50 1.0 ms），
比 FTS5 的 13.3 ms 还快。这也解释了 5.1 里 `pgvector` keyword p50 = 47.86 ms：
它是 37 条顺扫与 13 条走索引的混合，不是全文检索的固有代价。
（未复核：换成 `websearch_to_tsquery` 或加 `AND`/邻近约束后计划与质量会怎么变——**没测过，不写结论**。）

### 5.4 端到端检索延迟（含 bge 查询编码，仅作参考）

| 模式 | `sqlite` p50 / p95 | `sqlite-vec` p50 / p95 | `pgvector` p50 / p95 |
|---|---|---|---|
| hybrid | 63.7 / 100.8 ms | 79.2 / 93.4 ms | 120.8 / 169.4 ms |
| bm25-only | 15.6 / 29.6 ms | 14.8 / 27.3 ms | 53.2 / 92.1 ms |
| dense-only | 45.3 / 60.4 ms | 73.9 / 113.1 ms | 57.4 / 62.3 ms |

前两列来自 `data/eval/store_bench/eval_final_sqlite.json` 与 `eval_final_sqlite_vec.json`
（2026-10-08 那一轮，**本轮未重跑**）；`pgvector` 列来自 2026-10-09 的
`cli eval --store pgvector --json`（`eval_pgvector.json`）。三列不是同一轮测的，
只在**数量级**上可比。

端到端差异被查询编码（30~45ms/条）与机器状态淹没，**不要**用它判断索引快慢；
要判断快慢看 5.1。dense-only 的差值（`sqlite` → `sqlite-vec` +28ms）与 5.1 的存储层
差值同向；`pgvector` 的 hybrid 反而最慢（比 `sqlite-vec` 高约 41ms），因为它的全文路
在 37/50 条查询上退化成顺扫（5.3.5）。

### 5.5 过程中发现并修掉的两个真实退化

1. **SQLite 页缓存太小（5~12 倍）**：向量表 29MB，而 SQLite 默认页缓存 2MB，
   每次 KNN 都在穿透页缓存读盘。实测同一份数据、同一台机器：

   | 配置 | KNN top-10 p50 |
   |---|---|
   | 默认（2MB 缓存） | 66 ~ 147 ms |
   | `cache_size=-131072`（128MB） | **12.0 ms** |
   | `mmap_size=256MB` | 20.5 ms |
   | 128MB 缓存 + mmap | 20.6 ms（mmap 无益，故只调页缓存） |

   已落成 `KUBEDOCS_SQLITE_CACHE_KIB`（默认 128MB）并在 `SqliteVecStore.__init__` 应用，
   并有一条专门的测试守着它（去掉 pragma 该测试变红）。
2. **`dense_search` 里的 `COUNT(*)` 让每次查询翻倍**：`vec0` 的 `COUNT(*)` 本身是全表扫描，
   原先为了 `min(limit, n)` 而每次调用都算一次（p50 12ms → 31ms）。
   实测 `k` 大于行数时 `vec0` 只返回现有行、不报错，因此直接去掉这次 COUNT。

## 六、被证否的假设（重要）

**假设**："sqlite-vec 提供真实 ANN 索引，能把 numpy 暴力扫描换成 HNSW/IVF，因而更快。"

**证否**：`sqlite-vec 0.1.9` 的 `vec0` **不提供 ANN**（HNSW/IVF 在其 roadmap 上），
它是 C 实现的**穷举扫描**；本机 `EXPLAIN QUERY PLAN` 亦显示 `SCAN v VIRTUAL TABLE`。
在 18861×384 上实测（调好页缓存后）仍比 numpy/BLAS 慢约 **11 倍**
（20.3ms vs 1.83ms）——numpy 的 `matmul` 走 BLAS，是单次大矩阵乘，
而 `vec0` 是逐行取向量累加，本规模下后者没有优势。
（2026-10-09 同轮复核，两个后端一起测：**22.36ms vs 2.01ms，同样是 11 倍**，见 5.1 的表——
倍数稳定，绝对毫秒数随机器状态变。）

**那么为什么仍然把它设为默认**（诚实理由，不含"更快"）：

1. **一致性**：向量与块行同一事务，不存在"块写了、向量没写"的中间态；
   旧实现要靠 `finalize()` 重建 `.npy` 才能保证一致。
2. **可增删**：删除一篇文档从"重写 29MB 矩阵"变成"删几行"。
3. **内存**：向量不再常驻 Python 进程。
4. **少一个失配点**：没有 `.npy` 侧车文件就没有"库与矩阵不同版本"这类事故。

**代价同样明确**：本规模下向量检索慢约 11 倍（1.8ms → 20.3ms）。
若这条延迟比上面 4 条更重要，把 `KUBEDOCS_STORE=sqlite` 即可回到旧实现——
两个后端都在，且都有测试；这正是 D3「不删旧实现」的价值。

## 六之二、"换 HNSW 就能提速"在本量级上**同样不成立**

**假设**："给 pgvector 配上 HNSW，1.9 万块的向量检索会比 numpy 暴力扫描更快。"

**证否（2026-10-09 同轮实测）**：`pgvector` HNSW（`ef_search=200`）dense p50 **5.57 ms**，
而 numpy/BLAS 暴力内积是 **2.01 ms**——**HNSW 慢 2.8 倍**；`ef_search=100` 时是 4.29 ms，
也仍是 numpy 的两倍。原因是两边做的根本不是同一件事：

- numpy 那边是**一次 `matmul`**，18861×384×4B ≈ 29MB 矩阵走 BLAS，单机内存带宽下 2ms 到底；
- pgvector 那边是**图遍历 + 进程间往返**（哪怕连接池已就位，SQL 解析、计划、行编解码都在里面）。

公平地讲，HNSW 赢的是**它自己的精确扫描**：同一份数据上
`dense_search_exact()`（关掉索引扫描）p50 **51.79 ms** → HNSW 4.28 ms，**12.1×**，
与前一版的对照同向（原始数据 `eval_pgvector_attrib.json` 的 `dense_latency`）。
所以正确的表述是：

> **HNSW 的价值在"让数据库端的全表扫描不再必要"，不在"比进程内的 BLAS 快"。**
> 1.9 万块这种量级，进程内 numpy 就是最快的那条路；HNSW 的账要在百万级、
> 或"向量必须留在数据库里做多实例并发"的时候才算得过来。

这条与上一节（sqlite-vec 不是 ANN、却仍被设为默认）是同一枚硬币的两面：
**"换了索引类型"本身不是性能结论，测出来才是。**

## 九、pgvector 的已知质量落差与待决策项（**未决**）

### 9.1 落差是什么

**一句话**：`KUBEDOCS_STORE=pgvector` 时，混合检索在**同一份标注集上低于冻结基线**，
而这条落差**不是延迟、不是 HNSW、也不是可以靠调参消掉的**——它是"Postgres 核心没有 BM25"
的直接后果（5.3.3 的四条对照）。

| | 冻结基线（SQLite 后端） | `pgvector` | 落差 |
|---|---|---|---|
| hybrid hit@10 | 0.8400 | 0.7400 | **-0.1000** |
| hybrid recall@10 | 0.7600 | 0.6800 | **-0.0800** |
| hybrid MRR@10 | 0.5205 | 0.5157 | -0.0048 |
| bm25-only hit@10 | 0.7000 | 0.5400 | **-0.1600** |
| dense-only hit@10 | 0.7800 | 0.7800 | 0 |

### 9.2 现在这条落差**没有**被任何东西掩盖（这是刻意的）

- 冻结基线文件 `data/eval/retrieval_baseline.json` **没有**被改动，pgvector 也**没有**被
  写进新基线——所以 `cli eval --store pgvector --gate` **明着失败**：
  退出码 **2**，唯一失败项是 `hit@10 从 0.8400 掉到 0.7400（容差 0.02）`
  （MRR 0.5157 仍在容差 0.02 之内，所以没触发第二条）。这正是闸门该有的行为：
  **闸门红着，比悄悄放宽标准诚实。**
  （复现时**不要**加 `--json`：`run_eval` 里 `--json` 分支在闸门之前就 `return EXIT_OK`，
  于是 `--gate --json` 会静默跳过闸门、返回 0。这是 `evaluation/harness.py` 的一个真实
  缺陷，本次未修，单独记在交付说明里。）
- 没有为了让数字好看去调 RRF 的 `k`、候选队列长度或列权重——那些旋钮会同时改变
  SQLite 后端的数字，等于把"可比较"这件事弄坏。
- 顺带说明：这条落差**与 `ef_search` 无关**（100/200/400 的 hybrid 完全一样），
  所以"把 ef_search 从 100 调到 200"这个动作**不**是在修它，只是在修 HNSW 自己的召回。

### 9.3 四条候选路径（都没有替决策人拍板）

| 方案 | 依据（本 ADR 的实测） | 代价 / 未验证的部分 |
|---|---|---|
| **A. 装 ParadeDB / pg_search，引真 BM25** | 5.3.3 的对照表明"全文路换回真 BM25 后四项指标逐位回到基线（Δ=0）"，而 BM25 正是 FTS5 用的那个函数 | Postgres 镜像要换成 ParadeDB 版（或自行编译扩展），compose/CI/本地环境都要跟着变；扩展与 PG 版本的绑定、DDL 里 `tsv` 生成列要不要换成 `bm25` 索引、备份与升级路径——**一条都没测过**。这是"根治"方向，代价最大 |
| **B. 全文路仍用 FTS5，向量路用 pgvector（跨引擎混用）** | 5.3.3 里 `FTS5 全文 + pgvector 精确向量` 变体的四项指标**逐位等于基线**；`FTS5 + pgvector HNSW(ef=100)` 也只有 MRR/nDCG 低 0.0006 | 要真的实现一个"两路分属两个引擎"的 `Store`（本 ADR 的变体是一次性脚本拼的，不是产品代码）；后果是**双写**：摄取时块要同时进 SQLite 与 Postgres，删除/增量同步、事务边界、失败恢复全都要重做。D2 当初选 pgvector 的理由之一（"一库承担全文+向量"）就此作废 |
| **C. 另立一条 pgvector 基线** | 不需要改代码：harness 已有 `--baseline` 参数，`eval --store pgvector --baseline data/eval/retrieval_baseline.pgvector.json` 即可 | **这只是把红灯换成黄灯**：写一个"hit 0.74"的基线，等于把 -0.10 制度化。若要走这条，前提是决策人明确接受"pgvector 部署的检索质量比本地低 10 个点"，并把这条落差作为已知项长期跟踪（否则它就是"改基线让闸门变绿"，本项目明令禁止的那种做法） |
| **D. 维持现状：pgvector 的闸门保持红** | 现在就是这个状态 | 代价是 pgvector 一旦投入生产，就没有可用的质量闸门（红着的闸门没人看）。**本次选择的正是这一条**：先把落差、根因与代价写清楚，交给决策人，而不是替他把基线改掉 |

### 9.4 建议（供决策，不是决定）

若 pgvector 的上线诉求是"多实例写 + 一库承担全文与向量"，**A 是唯一能同时满足诉求与质量的路**，
但它的验证成本也最高（要重新灌库、重跑本节的四组对照）。若诉求只是"向量要留在数据库里、
且能水平扩"，**B 用最小的质量代价（Δ=0）换来了最复杂的运维**。
**C 不应当在没有明确接受落差之前做**——那是把问题从"指标"搬进"基线文件"。

无论选哪条，**本节的数字与 5.3 的对照表都应当被重跑一次再签字**：
它们来自 18861 块这一份索引、50 条标注，`ef_search`/内核版本/机器状态都只对当时那次运行负责。
