# ADR-0004：向量存储后端——默认嵌入式 ANN 位（sqlite-vec）+ 生产 pgvector

- 状态：已接受（本地默认已落地并实测；**pgvector 一路未验证**，见第七节）
- 日期：2026-09-26
- 相关：ADR-0001（技术选型：存储定为 Postgres+pgvector）、ADR-0002（先跑通业务逻辑：
  默认退回 SQLite+FTS5+numpy）、ADR-0003（双域 Agent 平台）
- 影响面：`src/kubedocs/store/`（新增两个实现 + 后端选择）、`config.py`（`KUBEDOCS_STORE`
  与 HNSW/页缓存参数）、`scripts/`（迁移与基准脚本）。`ingest` / `retrieve` / `generate` /
  `api` 的**检索与生成逻辑一行未改**（只把类型标注从 `SqliteStore` 换成 `Store` 协议）。

## 一、背景：ADR-0002 留下的两条边界到期了

ADR-0002 把默认存储定为"SQLite(FTS5) + numpy 暴力内积"，并写明三条代价：

| 边界 | ADR-0002 的原文 | 现在的状态 |
|---|---|---|
| 单写者 | 「线上多实例写 → 换 pgvector 版」 | 生产实现已补齐（本 ADR） |
| 无 ANN | 「超过 ~100 万块 → HNSW/IVF」 | 本地用 sqlite-vec 位替换，**但它不是 ANN**（见第六节） |
| 向量常驻内存 + 删除要重建矩阵 | 未写进 ADR-0002，是实现的隐含代价 | 新默认实现消掉了这一条 |

同时 ADR-0001 第三节「留待验证的假设」第 2 条（Postgres 全文检索对 K8s 文档的召回质量）
一直没有数据。本 ADR 给出**同一份标注集、同一批查询、同一批向量**下的两路对照——
但 pgvector 一路因环境（Docker 未起来）只能标注为未验证。

## 二、决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **新增 `SqliteVecStore`（SQLite + sqlite-vec），并把它设为本地/CI 默认** | 向量与块行同事务、可增删、不常驻内存、不需要 `.npy` 侧车文件 |
| D2 | **新增 `PgVectorStore`（Postgres + pgvector HNSW）作为生产实现** | 多实例写、一库承担全文+向量、schema 级多租户 |
| D3 | **旧实现 `SqliteStore` 保留**，不被删除 | 它是唯一"零扩展、纯 numpy"的实现，可回退；也是性能对照的基线（删掉这列数字就再也复现不了） |
| D4 | **后端由 `KUBEDOCS_STORE` 选择，默认 `sqlite-vec`；非法值直接报错，绝不静默回退** | 静默回退会让"我明明切到 pgvector 了，为什么数据还是旧的"变成一个没有日志的谜 |
| D5 | **`Store` 协议补齐运维操作**（`rebuild_from_scratch` / `verify_fts` / `meta_dump` / `doc_summary` / `close`），调用方类型统一到 `Store` | 协议不写全，pgvector 版就得靠 `cast`/`getattr` 绕过类型检查，等于把"可替换"作废 |

## 三、三个实现的定位与要点

| | `sqlite-vec`（默认） | `sqlite`（旧） | `pgvector`（生产） |
|---|---|---|---|
| 全文 | SQLite **FTS5** + `bm25()`，列权重 `(body 1.0, title 3.0, breadcrumb 1.5)` | 同左（**同一份索引、同一段代码**） | `tsvector`（生成列）+ GIN + `ts_rank` |
| 向量 | `vec0` 虚表，**主键 = `chunk_id`**，`distance_metric=cosine` | numpy 矩阵内积（`argpartition`） | `vector(384)` + **HNSW**（`vector_cosine_ops`） |
| 向量存放 | DB 内虚表，与块行**同事务** | `.npy` 侧车文件 + `finalize()` 重建矩阵 | 与块行同一行（`NOT NULL`） |
| 删除一篇文档 | 按 `chunk_id` 删除行 | 重建整份矩阵（18861×384 ≈ 29MB 重写） | `ON DELETE CASCADE` |
| 内存 | 不常驻 | 全量向量常驻（29MB） | 不常驻（服务端） |

### 为什么 sqlite-vec 用 `chunk_id` 当向量表主键

旧实现必须绕道 `chunks.rowid`，于是要处理"SQLite 会回收最大 rowid"这个坑
（`finalize()` 里重建矩阵并回写 `vector_row` 就是为了它）。直接用 `chunk_id`
作 `vec0` 的主键后，这个坑**不存在**：覆盖与删除都按主键定位，
不存在"行号错位"这种可能。

### pgvector 的 HNSW 参数（`m=16` / `ef_construction=64` / `ef_search=100`）

- `m=16`：每个节点的出边数，pgvector 默认值。1.9 万块规模下 `m=8` 会明显掉召回，
  32 以上收益递减而索引体积与建图时间线性上升。**只能重建索引才能改**。
- `ef_construction=64`：建图候选队列，默认值。与 `m` 一起决定图质量；
  本规模下建索引只需数秒，调到 200 的收益要在更大规模上才看得到。
- `ef_search=100`（默认 40，**查询期**参数，不需要重建索引）：这是"换后端不许
  让指标退化"这条纪律下买的保险——候选队列给足，召回贴近精确检索，
  而代价在本规模下很小。三者都通过 `KUBEDOCS_PG_HNSW_*` 可调。
- 距离用余弦（`<=>` + `vector_cosine_ops`）：与另外两个实现语义一致；
  向量已归一化时余弦序与内积序严格相同。

### 全文的**真实差异**（不粉饰，尤其中文）

1. **排序函数不同源**：FTS5 是真 BM25（含 IDF 与文档长度归一化）；
   Postgres 核心**没有 BM25**，用的是 `ts_rank`（TF 加权，无 IDF、无长度归一化）。
   列权重通过 `setweight` + `ts_rank(weights,...)` 对齐到同名权重，
   但**相同命中集合下的排序仍可能不同**——常见词与稀有词的相对权重不同源。
   要 BM25 得装扩展（ParadeDB/pg_search），本次不引入。
   实测的影响：见第五节（hit/recall/MRR/nDCG 全部未变，说明在本语料上差异未外显到指标层）。
2. **词干与停用词**：`english` 配置 = Snowball 词干 + 英文停用词表；
   FTS5 的 `porter` 只做词干、**不删停用词**。查询侧我们已自行去停用词，
   但索引侧 Postgres 会把纯停用词的行索引成空。
3. **分词器不同**：Postgres 默认解析器 vs FTS5 `unicode61`。
   对 `kube-apiserver`、`--eviction-hard`、`v1.29` 这类标识符两者都按非字母数字切，
   但边界情况（下划线、点号与数字组合）不完全一致。
4. **中文（必须写明）**：**Postgres 侧没有 jieba**。本实现的做法是把
   **应用层的归一化文本** `body_normalized`（中文域即 jieba 预分词结果）写进库，
   再 `to_tsvector('english', body_normalized)` 建索引。所以：
   - 中文**能**检索，但能力来自**应用层归一化器**，不来自 Postgres；
     与 SQLite 侧用的是同一个 `Normalizer`，因此两侧的中文切分一致；
   - `english` 配置会对中文词元跑 Snowball 词干（对 CJK 是空操作），无害；
   - 若把中文语料配 `normalizer=identity`，Postgres 与 FTS5 **一样**会把整句
     当成一个词元——这不是 Postgres 独有的缺陷；
   - 想在库内做中文分词需要 zhparser/pg_jieba 扩展，本次**未引入、未验证**。
5. **结构性优势**：`tsv` 是 `GENERATED ... STORED` 生成列，**不可能与正文漂移**；
   FTS5 是外内容表，删除顺序写错就会永久不一致（`sqlite_store.py` 文档第 1 条）。
6. 并列分数的次序：Postgres 侧显式按 `chunk_id` 定序（确定性）；
   FTS5 的并列次序由内部实现决定，不应依赖。

## 四、后端选择

```
KUBEDOCS_STORE=sqlite-vec   # 默认：本地/CI，零外部进程、零镜像、零网络
KUBEDOCS_STORE=sqlite       # 旧实现：回退与性能对照
KUBEDOCS_STORE=pgvector     # 生产：Postgres + pgvector（需 KUBEDOCS_DATABASE_URL 可达）
```

- 默认值写在 `Settings.store` 的类型化字段上（不是散落的 `os.getenv`），
  非法取值在**启动时**被 pydantic 的字面量校验挡住；工厂里再兜一层
  （防止有人绕过 `Settings` 直接调 `from_settings`）。
- 工厂延迟导入各实现：只想用 `sqlite` 时，不该因为缺 sqlite-vec 扩展
  或没装 psycopg 而起不来。
- **没有回退链**：`sqlite-vec` 扩展加载失败就报错，不会"悄悄换成 numpy 暴力扫描"。

## 五、实测（同一份 18861 块 / 384 维真实索引，同一台机器）

### 5.1 存储层延迟（`scripts/bench_store_latency.py`，top_k=10，各 150 次采样）

| 后端 | dense p50 | dense p95 | keyword p50 | keyword p95 |
|---|---|---|---|---|
| `sqlite`（numpy 暴力内积） | **1.83 ms** | **2.17 ms** | 12.20 ms | 23.15 ms |
| `sqlite-vec`（vec0，调大页缓存后） | 20.31 ms | 21.41 ms | **11.35 ms** | **22.59 ms** |
| `pgvector`（HNSW） | 未验证（见第七节） | — | 未验证 | — |

- 跨后端 **top-10 完全一致：向量路 150/150，全文路 150/150**。
- 样本为 50 条金标查询 × 3 轮 = 150；查询编码（bge，约 30~45ms/条）**不计入**延迟。
- 该脚本刻意**分别**测两路：交错测时向量路 p50 会从 13ms 涨到 21ms
  （FTS 与向量表的页访问互相挤占页缓存），那个数字既不是向量延迟也不是全文延迟。

### 5.2 换后端**没有**改变检索指标（`cli eval`，50 条金标，top_k=10）

| 指标（hybrid） | 改前 `sqlite`（冻结基线） | 改后 `sqlite-vec` | 差异 |
|---|---|---|---|
| hit@10 | 0.8400 | 0.8400 | **0** |
| recall@10 | 0.7600 | 0.7600 | **0** |
| MRR@10 | 0.5205 | 0.5205 | **0** |
| nDCG@10 | 0.5464 | 0.5464 | **0** |

单路消融也逐位相同：`bm25-only` hit 0.70 / MRR 0.3787；`dense-only` hit 0.78 / MRR 0.4253；
未命中条数同为 8 / 15 / 11；引用完整性违规 0。
`cli eval --gate` 在两个后端上都**通过**（与 `data/eval/retrieval_baseline.json` 的冻结基线比较）。

**为什么完全没变**：两个 SQLite 后端共用同一份 FTS5 索引与同一段 `keyword_search`
代码（全文路逐字节相同）；向量路在向量已归一化时"内积序 == 余弦序"，
且 vec0 是**穷举**扫描（不是近似），所以 top-k 也完全相同。
换句话说：这一路替换是**存储形态**的改变，不是**检索语义**的改变——这正是它可验证的原因。

### 5.3 端到端检索延迟（含 bge 查询编码，仅作参考）

| 模式 | `sqlite` p50 / p95 | `sqlite-vec` p50 / p95 |
|---|---|---|
| hybrid | 63.7 / 100.8 ms | 79.2 / 93.4 ms |
| bm25-only | 15.6 / 29.6 ms | 14.8 / 27.3 ms |
| dense-only | 45.3 / 60.4 ms | 73.9 / 113.1 ms |

端到端差异被查询编码（30~45ms/条）与机器状态淹没，**不要**用它判断索引快慢；
要判断快慢看 5.1。dense-only 的差值（+28ms）与 5.1 的存储层差值（+18ms）同向。

### 5.4 过程中发现并修掉的两个真实退化

1. **SQLite 页缓存太小（5~12 倍）**：向量表 29MB，而 SQLite 默认页缓存 2MB，
   每次 KNN 都在穿透页缓存读盘。实测同一份数据、同一台机器：

   | 配置 | KNN top-10 p50 |
   |---|---|
   | 默认（2MB 缓存） | 66 ~ 147 ms |
   | `cache_size=-131072`（128MB） | **12.0 ms** |
   | `mmap_size=256MB` | 20.5 ms |
   | 128MB 缓存 + mmap | 20.6 ms（mmap 无益，故只调页缓存） |

   已落成 `KUBEDOCS_SQLITE_CACHE_KIB`（默认 128MB）并在 `SqliteVecStore.__init__` 应用，
   并有一条专门的测试守着它（去掉 pragma 该测试变红）。
2. **`dense_search` 里的 `COUNT(*)` 让每次查询翻倍**：`vec0` 的 `COUNT(*)` 本身是全表扫描，
   原先为了 `min(limit, n)` 而每次调用都算一次（p50 12ms → 31ms）。
   实测 `k` 大于行数时 `vec0` 只返回现有行、不报错，因此直接去掉这次 COUNT。

## 六、被证否的假设（重要）

**假设**："sqlite-vec 提供真实 ANN 索引，能把 numpy 暴力扫描换成 HNSW/IVF，因而更快。"

**证否**：`sqlite-vec 0.1.9` 的 `vec0` **不提供 ANN**（HNSW/IVF 在其 roadmap 上），
它是 C 实现的**穷举扫描**；本机 `EXPLAIN QUERY PLAN` 亦显示 `SCAN v VIRTUAL TABLE`。
在 18861×384 上实测（调好页缓存后）仍比 numpy/BLAS 慢约 **11 倍**
（20.3ms vs 1.83ms）——numpy 的 `matmul` 走 BLAS，是单次大矩阵乘，
而 `vec0` 是逐行取向量累加，本规模下后者没有优势。

**那么为什么仍然把它设为默认**（诚实理由，不含"更快"）：

1. **一致性**：向量与块行同一事务，不存在"块写了、向量没写"的中间态；
   旧实现要靠 `finalize()` 重建 `.npy` 才能保证一致。
2. **可增删**：删除一篇文档从"重写 29MB 矩阵"变成"删几行"。
3. **内存**：向量不再常驻 Python 进程。
4. **少一个失配点**：没有 `.npy` 侧车文件就没有"库与矩阵不同版本"这类事故。

**代价同样明确**：本规模下向量检索慢约 11 倍（1.8ms → 20.3ms）。
若这条延迟比上面 4 条更重要，把 `KUBEDOCS_STORE=sqlite` 即可回到旧实现——
两个后端都在，且都有测试；这正是 D3「不删旧实现」的价值。

## 八、演进展望

| 触发条件 | 动作 |
|---|---|
| 本地向量检索延迟成为瓶颈 | `KUBEDOCS_STORE=sqlite`（numpy，1.8ms）或在 sqlite-vec 上做量化/分片 |
