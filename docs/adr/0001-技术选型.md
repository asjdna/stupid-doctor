# ADR-0001：技术选型与取舍

- 状态：已接受
- 日期：2026-09-24
- 背景：这是面向面试的**工业级工程作品**，评的是"选型判断 + 工程纪律"，不是"自己实现了多少算法"。

## 一、判定标准：什么该自研、什么该用成熟件

用一句话判据：**"市面有标准答案的通用基础设施 → 用成熟件；领域专有/需要实验证据的 → 自研"**。

| 部件 | 决定 | 理由 | 代价 / 已知风险 |
|---|---|---|---|
| 存储（向量+全文+业务） | **Postgres 16 + pgvector** | 一个库同时承担三件事：省一套运维、事务一致、能用 SQL 做混合检索 | 单机写扩展有限；千万级向量需换专用库 |
| 多路融合 | **自研 RRF（约 20 行）** | 逻辑简单、免标定、可单测；OpenSearch 内置策略与它同源，讲得清原理 | 丢掉分差信息，K 需按语料调 |
| LLM 网关 | **LiteLLM** | 多供应商路由/重试/回退/成本统计都是成熟实现，自研=重复劳动 | 多一层抽象；供应商特有参数需透传 |
| Agent 编排 | **LangGraph** | 需要"耐久状态 + 中断恢复"，自己写状态机与持久化不划算 | 图模型对简单流程偏重 |
| 嵌入 | **本地 BGE-small-en** | 医疗/企业语料常不允许出境；本地可离线复现，CI 不依赖密钥 | 冷启动要装模型；CPU 前向约 20ms/次 |
| 可观测 | **OpenTelemetry + Prometheus** | 标准协议、不锁供应商；Langfuse 作为可选后端 | 自托管 Langfuse 需额外一套 DB |
| 评测 | **自建金标闸门 + Ragas 对照** | 闸门纪律（能失败、拒绝跨集比较、基线溯源）框架给不了；行业口径用 Ragas 对齐 | 两套指标需在文档里说清口径差异 |

## 二、被否掉的备选

| 备选 | 为什么否掉 |
|---|---|
| 自研 BM25（jieba/rank_bm25） | 上一代项目已经写过一遍：**单次检索 248 ms**、暴力扫描、无 ANN。工业场景该用现成检索能力 |
| 自研 token 认证与限流 | 面试官会问"为什么不用标准"；接入标准认证还能讲 SSO/刷新令牌 |
| Elasticsearch/OpenSearch | hybrid+RRF 是现成的，但要再运维一套集群；本作品先用 Postgres 一库解决，规模上来再迁 |
| 纯内存/嵌入式向量库（FAISS/Chroma） | 无法演示"服务化 + 并发 + 持久化"，而这三样恰是工业要素 |
| 托管嵌入 API | 需要密钥且语料出境；作为**可切换选项**保留（`KUBEDOCS_EMBEDDING_PROVIDER=api`） |

## 三、留待验证的假设（不写"已完成"）

1. `docker compose up` 全栈可起——**本机尚未安装 Docker，未实测**；
2. Postgres `english` 全文检索对 K8s 文档（含大量代码/标识符）的召回质量——需金标实测；
3. 本地 BGE-small-en（384 维）是否够用——需与更大模型/API 做对照，用评测数据说话。

## 四、若规模上来（演进路径）

| 触发条件 | 动作 |
|---|---|
| 向量 > 100 万 | pgvector → 专用向量库（Qdrant/Milvus）+ ANN |
| 检索 P95 > 200 ms | 加倒排索引调优 / 上重排缓存 / 分片 |
| 多租户与权限 | 表级 RLS + 每租户独立 collection |
| 语料变中文 | 全文检索换 zhparser/pg_jieba 或应用侧 jieba 分词 + GIN 索引 |
